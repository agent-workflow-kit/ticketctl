# ticketctl: interface

Status: 0.1.0-design. The commands, including the write commands, are implemented; live verification (the live suites against a real site and the macOS checklist) remains. This document is the single normative source for ticketctl's rules; `docs/design.md`, the README and the architecture link to its headings and never restate its tables. The `--json` shapes, hook payloads, config, audit and log records are specified in [schemas/](../schemas/).

ticketctl is normalized ticket access for one ticket provider at a time. Jira Cloud is the only provider in 0.x. It reads tickets, searches them, lists transitions, comments, and performs writes (`transition`, `comment`, `comment-edit`, `comment-delete`, `create`, `update`, sprint add and remove) through one confirm-by-default write flow. It is stateless: it keeps a small cache and its audit and request logs, and no database.

## Concepts

### Identifiers

A ticket is identified by its key (`KEY-123`: an upper-case project key, a hyphen and a number). Input is case-insensitive and printed upper-case, because Jira resolves lower-case and numeric ids to the canonical key. A ticket may also be given as a browse URL; the rules are in [Site selection](#site-selection). `--json` output always uses the key plus a `site` field, never a URL as the identity. A ticket whose canonical key differs from the requested one (a moved ticket) carries `requested_key`; write results and audit use the canonical key.

Keys are not unique across sites. A key is resolved to a site by [Site selection](#site-selection); a command never guesses.

Every identifier that reaches a URL path, JSON, the audit or a hook payload has one grammar, and every grammar is matched with `fullmatch` (a trailing newline never passes). A ticket key, project key, site name or browse URL that fails its grammar exits 22 (`invalid_key`, `invalid_value` or `unknown_site`); a project or ticket key (and any other flag value) longer than 256 characters is `invalid_value`, not `invalid_key`, because the length check runs first; the shared flag grammars (actor, decision id, dedupe key, numeric ids, account ids, durations, integers) exit 2 `invalid_argument` (see [Commands](#commands)); an identifier in a provider response is dropped from its object and named in `incomplete`. Every URL path segment is built by one `segment()` helper that checks the grammar and percent-encodes with no safe characters, and every query parameter by one `query()` helper (urlencode, no safe characters). `segment()` also refuses `.` and `..` (which the dotted grammars allow) with the grammar's own failure. A `urlsplit` `ValueError` is exit 22 `invalid_value`, and so is a URL that holds a character at or below U+0020, U+007F or in the categories Cc, Zs, Zl or Zp (`urlsplit` would silently strip tab, CR and LF). The provider id and account id grammars exit 2 `invalid_argument` like the other shared flag grammars. Cache entries are validated on load and discarded on a mismatch.

| Identifier | Grammar |
|---|---|
| ticket key | `^[A-Z][A-Z0-9_]*-[0-9]+$`, at most 64 characters in all |
| project key | `^[A-Z][A-Z0-9_]*$`, at most 64 characters |
| site name | `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$` |
| provider ids (comment, field, property) | `^[A-Za-z0-9_.:-]{1,64}$` |
| numeric ids (transition, sprint, board) | `^[0-9]{1,18}$` |
| custom field id | `customfield_[0-9]+` |
| account id | `^[A-Za-z0-9:_.-]{1,128}$` |
| decision id and dedupe key | `^[A-Za-z0-9._:@/-]{1,128}$` |
| actor | `^(human\|auto):[A-Za-z0-9._@-]{1,64}$` |
| user time zone (`/myself`) | `^[A-Za-z0-9_+/-]{1,64}$`; a cache entry that fails it is discarded (callers test it with `Grammar.matches()`, never `check()`) |

Property keys are fixed by ticketctl and never built from caller text. `me.name` (and so the default actor) is normalized to the actor pattern at config load (disallowed characters become `_`, truncated to 64); an `--actor` that fails the pattern exits 2 `invalid_argument`.

### Site selection

A command picks its site with one table. The inputs are tried in this order and the first that selects a site wins:

| Order | Input | Result |
|---|---|---|
| 1 | `--site <name>` | an unknown name exits 22 `unknown_site` |
| 2 | a browse URL | the URL's lower-cased host (and port) must equal a configured site's, else exit 22 `unknown_site`; more than one configured site with that host and port exits 21 `ambiguous_site` listing them (`--site` resolves); a differing `--site` exits 22 `invalid_value` ("url and --site disagree") |
| 3 | a key, or `--project`, or the `create` project | the sites whose `projects` hold the project key: exactly one selects it, several exit 21 `ambiguous_site` listing them, none falls through |
| 4 | `default_site` | selects it |
| 5 | the only configured site | selects it |
| 6 | nothing selects | several sites exit 21 `ambiguous_site` listing the names; zero configured sites exit 2 (`invalid_config`, `reason: no_sites`) |

A browse URL must have the scheme `https` (`http` only for an `allow_http` site), no userinfo, and a path matching `^/browse/<KEY>/?$`, compared after `urlsplit`, never by substring. Its query and fragment are ignored (a pasted link often carries `?focusedCommentId=` or `#comment-1`); only scheme, host, port and path are checked, and a board or other URL form is not accepted. A command with several keys needs one site: keys, `--project` values or `--key` values that select different sites exit 22 `mixed_sites`, and `--site` forces one site for all keys. With zero configured sites, exit 2 `no_sites` wins over everything else, an unknown `--site` included. A browse URL is matched only on `/browse/<KEY>`: a site `url` with a context path never matches a browse URL, so use the key or `--site` there. A key from an unclaimed project goes to `default_site` or the only site by design; a user who wants a refusal claims all projects. ticketctl contacts only the selected site's host, and only hosts named in config. `sites resolve` (by KEY_OR_URL or `--project`) prints the exit 21 envelope with the candidates when ambiguous.

### Human actions

A write is confirm-by-default. A run is interactive when stderr is a TTY, `/dev/tty` can be opened, the actor is not `auto:` and `--yes` is not given. The answer is read from `/dev/tty`, never from stdin, so a piped body does not remove the human. The default actor is `human:<me.name>` when `/dev/tty` can be opened and stderr is a TTY, else `auto:unknown`; an explicit `--actor` always wins. `--body-file -` (or any `-` source) with stdin a TTY exits 2 `invalid_argument`. `actor_source` in the audit is `flag` (an explicit `--actor`), `tty` (the default became `human:` because of the controlling terminal) or `default` (the `auto:unknown` fallback). A dry-run and an apply may use different actors; the actor is not part of the plan hash, so a plan made under `auto:` can be confirmed with `--actor human:<user> --yes --expect-plan <hash>`.

The confirmation dialog is written to stderr through the output sanitizer, in this order: every outbound text value (title, description, comment body, `--set` and `--field` string values, labels), capped as described below, with the body rendered through the reader's Markdown renderer from the final ADF so every link shows as `text (href)` and the attribution paragraph shows; then any `from` value of a change (provider-owned text, a string or a list of strings, for every command: a `labels` change of `update` shows its list the same way), cut to 20 lines and 2000 characters with a "(N more characters, see --json)" marker; then the one-line-per-change summary and the warnings directly above the prompt. Everything sent is shown, and the engine enforces it before any dialog: every body hash in the plan (a step `body_sha256` or an entry of `bodies`) is the hash of a shown text, every change whose `to` is anything but null, an empty list or a non-empty list of strings (so a string, a number, a boolean, an object, or a list with any non-string item) has a shown text of the same label (for a string, the same text or a shown hash that is in the plan), and a list of strings is shown from the change itself, so an action must supply through the shown texts the rendered text of every non-string change value; a plan that breaks this is an internal error, never a dialog. Each value is introduced by a line that starts `value of <label> (sha256 <hex>):`, so no label can start a line that looks like a warning or a prompt. The dialog caps only what it displays (the sent text and the hashes are unchanged): a body, description or rich-text value shows at most 200 lines and 20000 characters, a title or a `--set` or `--field` string value (a multi-line value included, newlines shown as spaces) at most 500 characters, a list such as the labels shows every item up to 20000 characters in all (then a marker whose sha256 is the hash of the whole list joined with newlines), lines longer than 200 characters are folded (never inside a `<U+XXXX>` or `<redacted>` marker), runs of blank lines collapse to one, and every cut ends with a visible `[... N more characters; sha256 <hex>]` marker; the sha256 of the full final body is always shown, the sanitizer applies to everything shown, and `--dry-run --json` carries full values. When `--override-escalation` is given, the line `escalation override is ON: hooks that ask for review will be overridden by this answer` is printed directly above the prompt, followed by the names of the hooks it covers (every configured hook of the action and every `--hook`). Pending input on `/dev/tty` is discarded before the prompt (`termios.tcflush(fd, TCIFLUSH)`); only a typed `y` or `yes` (case-insensitive, trimmed) accepts, and anything else, an empty line, EOF and Ctrl-C decline. `--quiet` does not suppress the dialog. A decline is exit 20 `declined` (`retryable` false, `details.plan`) with no audit record, no hook and no pending record: it is a refusal by the human, not exit 13 (which means a human must still decide), so the caller stops. The prompt is `Send this? Type y or yes to accept, anything else declines [y/N]:` on the terminal; every line of an outbound text is shown after a `|` and a space so no ticket text can start a line that looks like a label, a marker or the prompt; the character counts of the cut markers do not count line breaks. The answer must be one ASCII line of at most 4096 bytes (a line that is not ASCII or longer declines, however many reads it arrived in; a partial line ended by Ctrl-D is not an answer by itself, but text typed before and after a Ctrl-D on the same line reads as that one line, as the human sees it), and the wait is 600 s, after which the run declines. If `/dev/tty` cannot be opened after the probe passed (it is opened `O_NOCTTY | O_NOFOLLOW`, must be a character terminal, and a failure opens nothing) the run is exit 13 `confirmation_required`, never an acceptance; the dialog is written to stderr and the question is read from `/dev/tty`, so they must be one terminal: when the foreground process group of stderr is not that of `/dev/tty` (stderr is on another terminal), or the descriptor cannot be waited on, the run is also exit 13, before anything is shown; an `auto:` actor is never asked, whatever the caller's probe says. SIGTERM and SIGHUP end the process before anything is sent.

`--yes` always requires `--expect-plan` from every caller (exit 2, `reason: yes_requires_expect_plan`); a caller takes the hash from the exit 13 envelope or a dry-run. With `comment` and `create`, `--yes` also requires `--dedupe-key` (exit 2, `reason: dedupe_key_required`); an interactive human may omit it. `--dry-run` skips these two checks (not `human_only`), so `--dry-run --yes` prints the plan and is the discovery route; every other flag-combination rule still runs first.

`--override-escalation[=ticketctl]` is human-only: it requires `--actor human:<user>` or no `--actor` with the default actor `human:`, and `--yes` may accompany it. With an `auto:` actor it exits 2 (`reason: human_only`). The claim is advisory (a same-user process can say `--actor human:x`); the audit records `actor_source`, `stdin_tty` and `inputs.override_escalation` (the scope, else null), so the claim is checkable. The flag overrides the escalation of every hook ticketctl ran (configured and `--hook`), never a veto. With the flag an interactive run prompts once (the dialog says the override is on and names the hooks it covers) and an escalation is then overridden; without it an interactive escalation exits 13 `escalated` and the message names the flag to re-run with. `--decision-id` values are caller-supplied and advisory like the actor; more than 16 of them exit 2 `invalid_argument`.

### Trust boundary

Allowing ticketctl in a session allows everything ticketctl can do with the user's credentials. Every control (confirmation, `--yes --expect-plan`, `pre-` hooks, the human claim, the mandatory attribution, the host list) is chosen by the caller through `--config`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME` and `HOME` (which redirect config and state), `--hook`, `--actor`, `--yes`, `attribution.enabled` and the environment, so "mandatory" and "human-only" are enforced only when the caller cannot choose arguments, environment and config. A caller that can run ticketctl can name a config with another host and a token variable of its choice and so send the token there, skip hooks (`--config` with no hooks), post as the user without the attribution line, run shell commands through `--hook`, pass a dry-run's own hash to `--yes`, and post any file the user can read with `--body-file` or `@file`. `HTTPS_PROXY` and CA variables are part of the same environment. The confirmation is not a boundary against a caller that can run ticketctl with a pty (`script`, `pty.fork` answer the prompt). The only constrained deployments are a wrapper that allows reads only (every write subcommand rejected, a fixed `--config`, a scrubbed environment) or writes executed outside the session, where the token lives. `--config` is not restricted to the user's config directory (the design guide defines it and tests need it). The audit is evidence for a cooperative caller and for writes, not a tamper-evident record (architecture non-goal): a read with a foreign `--config` is not audited, though it is logged with its host unless the state directory was redirected (see [Audit and log](#audit-and-log)). Read-only mode (below) is an accident guard inside this boundary, not a way out of it.

### Read-only mode

Read-only mode makes ticketctl refuse every write command. It is a deployment convenience that stops a mistaken or over-eager invocation (a script, an agent that wandered into `comment`) from posting: it is an accident guard and not a security boundary. A same-user caller controls `--config`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `HOME` and the environment (see [Trust boundary](#trust-boundary)), so it can run ticketctl with another config that does not set the mode, or send the request itself with the token it can read. What the mode does enforce is that, for a process that loads the config and environment the deployment chose, no write command reaches the provider. The constrained deployment of the trust boundary (a fixed `--config`, a scrubbed environment, a wrapper) is what makes that hold against a caller; the mode only adds a refusal that does not depend on the wrapper listing every subcommand, including write commands a later version adds.

Two switches turn it on, and either is enough: the config key `read_only: true` and the environment variable `TICKETCTL_READ_ONLY` set to `1`, `true`, `yes` or `on` (case-insensitive; `0`, `false`, `no`, `off` and an empty value mean "not set", and any other value is exit 2 `invalid_config` naming the variable, so a typo never leaves the mode off silently). Nothing turns it off once it is on in the same process: the environment cannot override a config `read_only: true` to false, a later `config.d/*.yaml` drop-in cannot override a `read_only: true` of `config.yaml` or of an earlier drop-in (the value is sticky across the files of one configuration), and there is no flag that does. A different `--config` file that names `read_only: false` (or none) is a different configuration and stays outside the guarantee: the mode is an accident guard.

When it is on:

- Every registry command of kind write (`transition`, `comment`, `comment-edit`, `comment-delete`, `create`, `update`, `sprint add`, `sprint remove`, and any later write command) exits 20 `read_only` before anything else: no provider request (not even the `/myself` read), no plan, no prompt, no hook, no lock, no audit record and no pending record. The check runs after the argv rules, so a usage error (exit 2) still comes first.
- `--dry-run` is allowed: it sends no write and reports the plan (the reads it does are the ones documented under [Write flow](#write-flow)).
- Reads, `export`, `fields refresh` and `validate` work. `export --to` and the cache, request log and audit files are ticketctl's own local bookkeeping, not provider writes, and stay allowed (`export --to` is documented as a local file write under [Input files](#input-files)).
- The gateway refuses locally, before any request is sent, any request whose method is not `GET` unless it is one of the three documented reads that need a POST: `POST /rest/api/3/search/jql`, `POST /rest/api/3/search/approximate-count` and `POST /rest/api/3/jql/parse`. This is the same exit 20 `read_only`; it makes the mode hold even if a command's own check were skipped by a bug.
- `validate` prints `read_only: true` (the key is absent when the mode is off, so no existing output changes).

### Unknown values

Unknown values are `null`, and a list that was cut off says so in `incomplete`. A consumer treats `null` as the safe answer: `blocked.value: null` is not "not blocked", `assignee: null` means unassigned or unknown according to `incomplete`, and a done-ness question is answered by `status.category`, never by `resolution` (a done ticket can have none).

## Normalized objects

Provider-neutral. No `customfield_N` name appears in any output except `fields list` output and the sanitized keys of a provider's `details.field_errors`: only mapped and `extra` fields do (see [Field mapping](#field-mapping)). Fields marked untrusted carry `x-untrusted` in the schemas; fencing remains the consumer's job, but ticketctl has already replaced control and invisible characters with visible markers (see [Sanitizing](#sanitizing)). Untrusted: title, description, `description_adf`, acceptance criteria, labels, link and parent summaries, comment bodies, attachment names, account display names, sprint names, changelog values and field names, extra string fields, plan `changes` values, error `message`, and `details.errorMessages`, `field_errors`, `errors` and `hook_stderr`. Status, type, priority and resolution names are workflow configuration, not ticket text, and are not marked (they still pass the sanitizer).

### Ticket object

`get` prints `{tickets, errors}` (see [`get`](#get-key)) and `search` prints the [Search result](#search-result); both hold the ticket shape of `schemas/defs.json#ticket`. `--fields` takes a comma list of the property names below and only property names (`fields` selects the configured extras, `comments` needs `--comments N` and `description_adf` needs `--include-adf`, otherwise exit 22 `invalid_value`); `key` and `site` are always present, an unknown name exits 22 `unknown_field`, and the provider request is built from the same list, so unrequested properties are neither fetched nor printed. `blocked` pulls `links` and `epic` pulls `parent`. `get` returns every property except `comments` (only with `--comments N`) and `description_adf` (only with `--include-adf`). `search` returns `key`, `title`, `status`, `assignee`, `priority`, `estimate`, `sprints`, `parent`, `updated`, `labels`, `type` by default; `due_date`, `created`, `links`, `blocked` and `epic` are requested by name.

| Property | Type | Notes |
|---|---|---|
| `key`, `site`, `url`, `id` | string | `id` is the provider's own id; `url` is the browse URL. |
| `requested_key` | string | present only when the canonical key differs from the requested one (a moved ticket). |
| `type` | `{name, subtask}` | |
| `title` | string | untrusted |
| `description` | string or null | untrusted; Markdown rendered from the provider's rich text. `description_adf` only with `--include-adf`: an opaque, untrusted object (a sanitized copy of the provider's document), or null when the ticket has no description. |
| `status` | `{name, category}` | `category` is `new`, `indeterminate` or `done`. |
| `resolution` | string or null | |
| `assignee`, `reporter` | `{account_id, display_name}` or null | no email address is ever printed. `account_id` is null for an account with no id (deleted, app or anonymized users), and the display name is then `unknown user`. |
| `priority` | `{name, rank}` or null | `rank` is the zero-based position in the provider's priority list (cached, see [Files](#files)); "Not Set" is a real entry with a rank; a name not in the list has `rank: null`; `priority` is null only when the issue's field is null. |
| `estimate` | number or null | the mapped `estimate` field; null with `incomplete: ["estimate"]` when it is ambiguous (see [Field mapping](#field-mapping)). |
| `acceptance_criteria` | string or null | untrusted Markdown; null without a mapping. |
| `labels` | string[] | untrusted; labels matching `^tc-[0-9a-f]{16}$` (the dedupe labels) are never listed. |
| `sprints` | `{id, name, state, start, end}[]` | `state` is `future`, `active` or `closed`; times UTC. |
| `parent` | `{key, type, title}` or null | the issue's parent; `title` only when the provider embeds it. |
| `epic` | `{key, type, title}` or null | set only when the parent's type is an epic (hierarchy level), else null; for a sub-task null (no extra read). The mapped `epic` field fills it only on sites where the parent is not the epic. |
| `links` | `{type, direction, key, status_category, summary}[]` | `type` is the link type's name. `direction` is relative to this ticket: `inward` means this ticket is the target of the link type's inward phrase (for `Blocks`, "is blocked by"), `outward` means it is the source ("blocks"). `status_category` and `summary` may be null; `summary` is untrusted. |
| `blocked` | `{value, by}` | `value` is `true`, `false` or `null`; `by` lists the keys. See [Blocked](#blocked). |
| `due_date` | date or null | `YYYY-MM-DD`. |
| `created`, `updated`, `resolved` | UTC ISO 8601 with `Z` to the second, or null | the provider's offsets (for example `-0600`, without a colon) are parsed and normalized and its milliseconds are dropped. |
| `comments` | `{items, total, truncated}` | only with `--comments N`; untrusted bodies. |
| `attachments` | `{id, name, size, mime}[]` | metadata only; `name` is untrusted. |
| `fields` | object | the configured `extra` fields, converted by schema. |
| `incomplete` | string[] | parts that were cut off or unavailable (`links`, `comments`, `attachments`, `<part>.truncated`, `<part>.invalid_id`, `links.unreadable`, `fields.<name>`, ...), sorted. Printed when requested (an empty list then) and whenever it is not empty. |

Text longer than a field's cap is cut at a code-point boundary, ends with the marker `<truncated>`, and the part is named `<field>.truncated` in `incomplete`; a comment object carries `truncated` (boolean). Caps: title 4096, parent and link summaries 4096, body fields 1,000,000, label 256, names 256, attachment names 1024. One ticket that fails to parse or convert becomes a stub with `incomplete`, never aborting a `search` or a multi-key `get`. `get --comments N` costs one extra `/comment?orderBy=-created` call per ticket and returns the latest N (at most 50), oldest first.

#### Unreadable parts

A property that cannot be read from the payload is never guessed: a scalar or object becomes `null`, a list `[]` and the part is named in `incomplete` (the part is the property name, `<part>.truncated` for text cut at a cap or a renderer budget, `<part>.invalid_id` for an identifier outside its grammar that was dropped; a name cut at its cap names `<part>.truncated` for `type`, `status`, `priority`, `resolution`, a link type, a parent or epic type and an account name). `id`, `url`, `type`, `title` and `status` have no null in the schema, so they are omitted and named instead (a status category outside `new`, `indeterminate` and `done` counts as unreadable); `description_adf` is likewise omitted and named when the description is not an object (`description_adf`) or the copy hit its node budget (`description_adf.truncated`), and is null only when the ticket has no description. An absent or null `reporter`, `created`, `updated`, `resolved`, `due_date` or `resolution` is null and an absent sprint field an empty list, in both cases without a name in `incomplete`; the property is named only when the value is present but unreadable. An account whose `accountId` is missing has `account_id: null` and the display name `unknown user`; an `accountId` that is present but outside its grammar does the same and names `<part>.invalid_id` (`assignee.invalid_id`, `reporter.invalid_id`). A list the provider did not send (`labels`, `links`, `attachments`) is unknown, not empty. A logical field that is ambiguous, or mapped to a field the list lacks, is named and warned about in every read that requests it; one that is neither mapped nor discoverable is named only when `--fields` asked for it. `epic` is the parent when the parent's `issuetype.hierarchyLevel` is 1 (null and named when the level is missing), else the mapped epic-link field's key when there is one. A parent with no embedded type has `type: "unknown"`. `description_adf` is a copy that keeps the key order, with every string and key sanitized, scrubbed and cut at 1,000,000 characters (a cut names `description_adf.truncated`), and non-finite numbers and integers above 2^63 in absolute value replaced by null (named `description_adf`, as is a key that collides with another once sanitized). `incomplete` also holds `ticket` for a stub (the payload had no usable `fields`, or was not an object but the caller named the key); a stub carries `requested_key` when the canonical key differs from the requested one.

#### Blocked

`blocked.value` is `true` when any `inward` link of a type listed in `sites.<name>.blocking_link_types` (default `["Blocks"]`, matched by link type name, case-insensitively) has an other end whose `status_category` is not `done`, even when the list was cut off (`true` wins over `null`). A null category counts as not done: the key is listed in `by` and `incomplete` gains `links.unreadable`. Otherwise it is `false` only when links were requested, none was cut off and none qualifies, and `null` when `links` was not requested or was cut off. It is computed from the links embedded in the same read; no extra calls.

### Comment object

`schemas/cli/comments.json`: `id`, `author` (`{account_id, display_name}`), `own` (true when the author is the resolved `me`), `created`, `updated` (equal to `created` when never edited), `body` (untrusted Markdown), `truncated`, `dedupe_key_sha256` and `body_sha256` (from the ticketctl property when present, else null), `authored_by_ticketctl` (true when the property is present on an own comment; an own comment whose `properties` the provider did not send as a list fails closed: true, `actor_kind` and both hashes null, and `comments` named in `incomplete`) and `actor_kind` (`auto`, `human` or null). The property key is compared exactly: a key that differs in case or spelling is not the property, and a property whose value is damaged (not an object, a `v` other than the number 1, a boolean `v`) still counts as present on an own comment. Listed oldest first by default; `--newest-first` reverses. A page is ordered by `created` (the id breaks a tie) whatever order the provider sent, a repeated comment id is kept once (naming `comments`), and a `total` the provider did not give makes `truncated` true and names `comments`.

### Changelog object

`schemas/cli/changelog.json`, entry shape `schemas/defs.json#changelog_entry` (a later `get` part can reuse it): `id` (the provider's history id), `author` (`{account_id, display_name}`, the same rules as a comment's author), `created` (UTC with `Z`, to the second) and `items`, one per changed field: `{field, from, to}`. `field` is the logical or `extra` name when the site maps the changed field (matched by the item's field id, see [Field mapping](#field-mapping)), else the fixed name of a system field (`status`, `resolution`, `assignee`, `reporter`, `priority`, `labels`, `title` for the summary, `description`, `due_date`, `parent`, `type`), else the provider's display name; a custom field id never appears (a display name that holds one shows the marker `<id>`). `from` and `to` are the old and new value, typed by the field and never by the content: `status`, `resolution`, `priority`, `type` and every other field give the value's text (or null when there was none), `assignee` and `reporter` an account object (null when there was none; the id comes from the id key and the display name from the text key, and an id outside its grammar gives `account_id: null` and names `changelog.invalid_id`), `labels` a list of label strings (the dedupe labels `tc-<16 hex>` are never listed: the drop is exact, so a real label of that shape is dropped too; that names `changelog` only when such a label is on one side of the `from`/`to` pair alone, since it was then added or removed and a real label may have been hidden, and a ticket that carries it on both sides names nothing; the entry may then show identical `from` and `to` lists), and a mapped sprint field a list of `{id, name}` (`name` null when the provider's names do not pair one to one with its ids: the lists must be of equal length and no name element may be empty; `id` null for an entry that is not a number, which includes an id of more than 18 digits; either loss names `changelog`). The provider's text is preferred to its ids (a status shows as `In Progress`, never its id). Text is untrusted and passes the sanitizer; a single-line value is cut at 4096 characters, a `description` at the body cap, a name at 256, each cut ending `<truncated>` and naming `changelog.truncated`. An entry whose id or `created` is unreadable is dropped and named (`changelog`, or `changelog.invalid_id` for an id outside its grammar); an item with no readable field name, or a value of a type the provider never sends (a number, an object), is dropped or null and names `changelog`; at most 200 items of an entry are kept (`changelog.truncated`); a repeated entry id is kept once (`changelog`). Entries are ordered by `created` with the id as the tie-break.

### Transition object

`schemas/cli/transitions.json`: `id`, `name`, `to` (`{name, category}`), `required_fields` (`{name, kind, allowed_values?}[]`, where `kind` is the provider's field type name, a free string of at most 64 characters), `has_screen`. Transitions are global on the supported provider (the same ids apply from every status), but ticketctl always reads the live list for the ticket and never relies on that.

### Sprint object

`schemas/cli/sprints-list.json`: `id`, `name`, `state` (`future`, `active` or `closed`), `start`, `end` (null for a future sprint), `board` (the origin board id, an integer; a listing by board may show sprints whose origin differs). The selector word `open` means state `active`; `sprints list --state` takes the state names.

### Search result

`schemas/cli/search.json`: `{tickets, truncated, next, count}`. `truncated` is true whenever more matches exist than were returned (`--limit`, the 500 cap or the request cap stopped the loop) and `next` is then set, except for `--limit 0 --count`, which returns no tickets and answers `truncated` true (when the count is above zero) with `next` null; `next` is the opaque cursor that `--cursor` accepts, else null; `count` is approximate (from the approximate-count endpoint) and present only with `--count`.

### Field mapping

Logical field names are fixed: `estimate`, `acceptance_criteria`, `sprint`, `parent`, `epic`, `labels`, `priority`, `assignee`, `resolution`, `due_date`. Each site maps a logical name to a provider field by `{name}`, `{id}` or `{schema}` under `sites.<site>.fields`, and `fields.extra.<name>` adds more fields to the output. The schema string is `schema.custom` (the `type` for system fields).

- **Discovery without a mapping.** `sprint` is the field whose `schema.custom` ends `:gh-sprint`. `estimate` is the union of fields whose `schema.custom` ends `:jsw-story-points` and fields with `schema.custom` `…customfieldtypes:float` and the exact name `Story Points` (the legacy points field has only the generic float schema). `epic` uses `:gh-epic-link`. `acceptance_criteria` has no default: null and no error unless mapped, and `incomplete` names it only when requested. The field list is cached ([Files](#files)).
- **The field list is untrusted.** `GET /field` must answer a JSON array of at most 10,000 entries, else exit 12 `provider_changed`. An entry without a string `name`, with a `custom` that is present but not a boolean, or with an `id` outside `^[A-Za-z0-9_.:-]{1,128}$` is ignored (a warning counts the ignored entries, without naming them), every entry of a duplicated `id` is dropped, names and schema strings are sanitized and capped (name 256, `schema.type` and `items` 128, `schema.custom` 256), and a schema that is not an object with a string `type` is unknown (null). A mapping by `name` is an exact, case-sensitive match on the sanitized name, by `id` an exact match, by `schema` an exact match on the schema string; a mapping always beats discovery, even when it finds nothing. System fields (`parent`, `labels`, `priority`, `assignee`, `resolution`, `due_date`) are the non-custom fields with the ids `parent`, `labels`, `priority`, `assignee`, `resolution` and `duedate`. A cached list that is not valid under the same rules is deleted and refetched; the cache read is stricter than the provider read and also refuses a `custom` that is not a boolean, a `schema` that is not an object or null, and any entry whose sanitized name or schema differs from what is stored. A mapping that names a field the cached list lacks refetches the list once (a fresh list is never refetched, and neither is a cached list fetched within the last 60 seconds, so a mapping that stays missing does not cost a fetch on every command), so a field created after the cache was written is not reported missing.
- **Ambiguity is lazy.** More than one candidate for a logical field exits 21 `ambiguous_field` only when the requested output or a write needs it. A read that requests it (default `get` includes `estimate`) prints the property as null with `incomplete: ["estimate"]` and warns; a write to it exits 21. The candidates in `details.candidates` and in `fields check` are display names (never ids), sorted, at most 50; a name shared by candidates gets its schema string appended (the name part is cut so the schema string is never cut off, and a label never exceeds 256 characters). A candidate label that holds text matching `customfield_[0-9]+` shows the marker `<id>` in its place.
- **Names for `--set` and `--field`.** A name resolves in order: the logical names left, the `extra` names, then a unique exact display name from the metadata (case-insensitive), the metadata being `editmeta` for `update`, the transition's field list for `--field` and `createmeta` for `create`. The refusal is then judged on the resolved provider field, never on the typed token: the fields that have a dedicated flag or command (`assignee`, `labels`, `resolution`, the summary (the title) and a sprint field, schema `:gh-sprint`), `reporter` (settable nowhere) and, by command, `description` (accepted on `update` only; on `create` the body is `--body-file`) and `parent` (refused on `create`, which has `--parent`) are refused, so `Labels`, `Summary`, `Assignee`, `Sprint`, `Resolution`, `Parent` and `Reporter` in any case refuse exactly like their logical names (the typed `title` too). A refusal, or a field given twice (compared by resolved field, so two spellings of one field count), exits 2 `invalid_combination` and the message names the flag or command (for `reporter`, that it cannot be set). A `customfield_N` id is refused (`unknown_field`) unless a logical name (by config or by discovery) or an `extra` name maps to it; an ambiguous display name exits 21 `ambiguous_field`.
- **Missing.** A mapping that names a missing field is reported as the `missing` problem by `fields check` and `validate --probe` (both exit 0), and a command that needs it exits 22 `unknown_field`.
- **Conversion by schema.** Rich text (ADF) to Markdown, an option to its string, a user to an account object, an array to a list, a number to a number, date and datetime to ISO strings, labels to a list, an array of objects to a list of their `name` or `value`. Any other schema type gives null with `incomplete: ["fields.<name>"]`. A value that does not fit its schema (a string where a number is declared, an unreadable date) is treated the same way. Datetimes become UTC with `Z` to the second, a naive datetime is unknown, an extra plain string is single-line text, an extra rich text (ADF rendered to Markdown) keeps its rendered line breaks, both are cut at 4096 characters, and an array is cut at 1000 items, any cut naming `fields.<name>.truncated`; `acceptance_criteria` is body text instead (plain strings keep their line breaks, and plain or rich text is cut at the body cap of 1,000,000 characters); a number that is an integer above 2^63 in absolute value is unknown (null with `incomplete`); an array whose item type is number, date or datetime converts each item the same way; a user conversion never reads `emailAddress` (display names pass through as sanitized text).

#### Value grammar

`--set name=value` and `--field name=value` split at the first `=`. The value is inline text, `@path` (the whole file; one trailing newline is stripped for scalar types) or `-` (stdin). Mismatched forms exit 22 `invalid_value`. Allowed values are checked when the metadata lists them, else the provider decides.

| Schema type | Accepted value |
|---|---|
| string | as given |
| number | `^-?[0-9]+(\.[0-9]+)?$` |
| date | `YYYY-MM-DD` |
| datetime | RFC 3339 with `Z` or an offset |
| option | the option name, matched case-insensitively against the allowed values (several matches or none: exit 22 `invalid_value` listing candidates) |
| array of option or string | a JSON array of strings, or a bare value meaning a one-element list |
| user | `me`, `none` (exact lower case; `ME` and `None` are refused) or an account id |
| issue link (`parent`) | a ticket key, sent as `{"key": KEY}` (`parent=` clears) |
| rich text | only `@path` or `-`, converted like a body (an inline value is exit 22 `invalid_value`) |

An empty value (`name=`) clears an optional field (null; an empty list for arrays); a required field refuses it. For an `auto:` actor a rich-text value is refused (see [Attribution](#attribution)).

Edge rules. A `--set` or `--field` argument with no `=`, an empty name, a name with a control or invisible character, a name over 256 characters, an `@` with no path, more than 100 assignments or the same typed name twice exits 2 (`invalid_argument`, or `invalid_combination` for the repeat); an inline value over 1,000,000 characters exits 22 `invalid_value`. A value that starts with `@` is always a file (there is no escape; put the text in a file). `@-` is a file named `-`, never stdin. A file or stdin that is empty (after the one stripped newline) is refused, so only `name=` clears. A string value is one line of at most 4096 visible characters and not blank (a value of only spaces exits 22 `invalid_value`), a number has at most 17 digits after the sign when it has a fraction (an integer at most 2^63, 19 digits), a number whose fraction a 64-bit float cannot hold exactly (such as `1234567890123456.7`) is refused, a datetime is sent in UTC as `YYYY-MM-DDTHH:MM:SS.mmm+0000`, an option field with no listed values sends the text and the provider decides, a priority sends its `name`, a list element of a component or version field sends its `name`, a user list takes account ids and `me` (not `none`), and a field of any other type exits 22 `invalid_value`. A configured secret in a value exits 22 `secret_in_body`; it is looked for in the text, in every decoded list item and in every string of a converted rich-text document. A datetime outside the range of years 1 to 9999 in UTC exits 22 `invalid_value`. The checks run in the order: global flag combinations, the one-stdin rule, the `--set` and `--field` grammar and offline refusals, then the default actor (which may read the configuration), so a configuration problem never hides a usage error. No error message carries the value.

## Sanitizing

Every string that leaves the process (`--json` values, stderr, `--verbose` output, hook stderr relayed in an envelope, `export`) and every outbound string value (title, label, field string, body text node) passes one sanitizer, whatever its origin: provider text, caller input echoed in an error, file paths. It replaces by `<U+XXXX>` every code point in the categories Cc (except `\n` and `\t` in body-class fields), Cf, Cs, Co, Cn, Zl and Zp, plus U+034F, U+115F, U+1160, U+16FE4, U+17B4, U+17B5, U+180B to U+180F, U+2800, U+3164, U+FE00 to U+FE0F, U+FFA0, U+E0100 to U+E01EF and U+FFFC. The body-class fields are a closed list: descriptions, comment bodies, acceptance criteria, rendered ADF and rich-text `changes[].from` and `to`; everything else, including `hook_stderr`, extra string fields and error text, is single-line. A lone `\r` and CRLF are first normalized to `\n` in both field classes; then in body-class fields `\n` and `\t` stay, and in single-line fields `\n` and `\t` become one space each (so CRLF, and a bare `\r`, is one space). No Unicode normalization is applied (it would change provider names that consumers compare by equality). The `<U+XXXX>` marker is not escaped in input, so a consumer must not read a marker as proof of anything. Over-long text is cut as described under [Ticket object](#ticket-object). ticketctl does not escape Markdown or fence text; that is the consumer's job (architecture §13.2 rule 1). A key, account id or other identifier that fails its grammar is rejected, and the rejection message prints the sanitized value cut to 64 characters. The rule is category based, so joiner and variation-selector sequences (emoji, Persian text that needs U+200C) are shown and written with markers (see [Residual risks](#residual-risks)). Output scrub: the last step of the one output path, after the sanitizer and before any text is printed, logged, audited or relayed (stdout, stderr, `--verbose`, `TICKETCTL_DEBUG` tracebacks, the log, the audit, `export` and hook stderr), replaces every occurrence of a configured token value (at least 8 characters once stripped of surrounding whitespace) and of the Basic authorization header value (the base64 of `email:token`) by `<redacted>`. The scrub also covers the percent-encoded forms of each value (`quote` with and without safe characters) and its JSON-escaped form, merges overlapping matches into one `<redacted>`, and runs before any cut to a field cap, so a value that straddles a cap leaves no prefix.

## Text conversion

### Reading

The provider's rich text (ADF) is rendered to Markdown with one list of rules:

- Blocks: `table` as pipe-table rows (header from the first row, at most 200 rows, cells flattened, escaping only `|`; rows beyond 200 are cut and followed by `[N more rows not shown]`), `taskList` and `taskItem` as `- [ ]` and `- [x]`, `hardBreak` as a newline, `rule` as `---`, `panel`, `expand` and `nestedExpand` as a block quote with the title first.
- Inline: `emoji` from `attrs.text` else `:shortName:`, `status` and `date` as their text, `mention` as `@name`, marks `strong`, `em`, `code` and `strike` as Markdown; other marks are dropped.
- Links: a link whose real `href` differs from its text renders `text (href)` with the href percent-encoded for `)`, spaces and control characters. `inlineCard`, `blockCard` and `embedCard` render the URL under the same rule. Only `http`, `https` and `mailto` keep their target; any other scheme, and any href or card URL longer than 2048 characters, renders `[unsafe link removed]`.
- Media nodes render `[attachment: <id>]` when the id matches `^[A-Za-z0-9-]{1,64}$`, else `[attachment: ?]`. An unknown node renders `[unsupported: <type>]` (the type when it matches `^[A-Za-z]{1,32}$`, else `unknown`) followed by its plain text.
- Budgets: depth 50 (`[too deep]`), 50,000 nodes and 1 MiB of output (`[too large]`, and `incomplete` names the part). The renderer never raises: the node budget also ends the text with `[too large]`, and an internal failure keeps the text rendered so far and ends it with `[render error]`. The renderer's `incomplete` carries the bare part name (the consumer maps it to `<part>.truncated`) and its reasons are `too_deep`, `too_many_nodes`, `too_large`, `table_rows` and `internal`. Text is not escaped (a literal `*` and a bold mark look the same); the consumer fences.

### Writing

Bodies are Markdown from `--body-file <path>` or `-` (stdin). `comment` also takes a short `--body <text>` for humans, treated as untrusted like the file form. ticketctl converts the Markdown to ADF with its own converter. The dialect is a CommonMark subset: paragraphs, ATX headings, bullet and ordered lists (nesting 5), fenced code blocks (with a language word), block quotes, inline code, bold, italic, `[text](http(s)://...)` links, and backslash or two-space hard breaks. Lists and block quotes together nest at most 5 deep (a deeper marker is literal text), a soft line break is one space, a link has no title, and a language word that fails the allowlist pattern is dropped. Tables, task lists, strikethrough, images, autolinks, raw HTML, `@` mentions, `[~accountid:...]` and Jira wiki markup stay literal text in ADF text nodes. The converter never creates mention, inline-card, media, panel or status nodes, and mark spans never nest links. `--format adf` accepts a prepared ADF document. Every rich-text value from any path (a body, a description, a `--set` or `--field` value) ends in one function `validate_adf()` against the [ADF allowlist](#adf-allowlist), and the write flow runs it again on every ADF document in a request body just before the request is made (a guarded gateway, so an action cannot skip it). A mapping with both `version` and `content` keys is treated as a document and validated, so a non-ADF payload with that shape is refused. The provider's wiki-markup string API is never used, because it parses `*x*`, `h2.`, `#` lists, `{code}` and `[~accountid:...]` out of a body.

Where the converter deviates from CommonMark it leaves text literal. A link target that is not a safe `http` or `https` URL leaves the whole `[text](target)` construct literal: a malformed authority, userinfo, a backslash or a control character in the target, a target over 2000 characters after the scheme (so 2007 or 2008 in total), an empty host, a host with `%`, a port that is not 1 to 5 ASCII digits, an IPv6 literal that is not an IPv6 address, an IDNA host that the `idna` codec would remap (`faß.de`), and whitespace around a destination. Only a non-ASCII host that the `idna` codec rejects raises, as exit 22 `invalid_value`. A link whose text has no visible (non-whitespace) text is also literal. A Markdown body that converts to more than 5000 nodes is exit 22 `body_too_large` (the converter checks this before `validate_adf()`, so for Markdown the node limit is reported by the converter), and input over 4 times `limits.body_chars` characters is `body_too_large` before any parsing (this holds for `--body`; a `--body-file` or stdin input over 4 times `limits.body_chars` bytes is refused earlier by the file reader as exit 22 `invalid_file`, "too large"). The converter takes the attribution paragraph as a reserve (its text length and its 2 nodes, a paragraph and a text node), so the size and node limits count it. The remaining deviations: no lazy continuation lines, no setext headings, no indented code blocks (the indentation is dropped and the text stays), no entity decoding, and thematic breaks stay text. Text made only of `<U+XXXX>` sanitizer markers is text for the emptiness rule, so a body of one control character is not `empty_body`.

The size is measured on the final document: the sum of the characters of all text nodes of the ADF that will be sent, after sanitizing, after the attribution line and after conversion, must be at most `limits.body_chars` (default 30000, schema maximum 32767, the comment limit verified for a single text node; the total across nodes is assumed, and the same cap applies to descriptions and rich-text custom fields, whose limit is unmeasured). Over is exit 22 `body_too_large`, never truncated or split into several comments; an empty body (no text, judged before the attribution paragraph is added) is `empty_body`. The hash of a body (plan, hook payload, audit, dedupe `body_sha256`) is the sha256 of the final ADF as canonical JSON (sorted keys, separators `,` and `:`, UTF-8, no ASCII escaping), for Markdown and `--format adf` alike. The provider does not sanitize written ADF (it stores `javascript:` links and control characters as given), so the allowlist and the sanitizer of [Sanitizing](#sanitizing) are the only defenses.

#### ADF allowlist

`schemas/adf.json` is the JSON Schema of the allowlist. Allowed nodes: `doc` (version 1), `paragraph`, `text` (non-empty), `heading` (`level` 1 to 6), `bulletList`, `orderedList` (`order` an integer 1 to 9999), `listItem`, `codeBlock` (`language` matching `^[A-Za-z0-9+#._-]{1,32}(?![\s\S])`), `blockquote`, `hardBreak`. Allowed marks: `strong`, `em`, `code`, and `link` (`href` matching `^(?!https?://[^/?#]*@)https?://[\x21-\x5b\x5d-\x7e]{1,2000}(?![\s\S])` with `fullmatch`: printable ASCII only and no backslash (browsers read `\` as `/`, so `http://evil.example\.trusted.example/` would change the host), userinfo refused, no other attributes; at most 2000 characters after the `http(s)://` scheme, so 2007 or 2008 in total; the patterns end in `(?![\s\S])` rather than `$` so a trailing newline never matches under any validator). The converter percent-encodes non-ASCII path characters and converts a non-ASCII host with the `idna` codec (a failure is exit 22 `invalid_value`); homograph hosts are a residual risk. Every other node, mark, attribute or attribute value is refused and never repaired (exit 22 `node_not_allowed`, `details.field` naming the path). Limits that the schema cannot express: depth 10 and 5000 nodes. Depth is counted over `bulletList`, `orderedList`, `listItem` and `blockquote` nodes only (a list and its item count 2, so five nested lists are depth 10); `validate_adf()` counts it the same way as the converter. Text nodes pass the sanitizer: a text node the sanitizer would change (a control or bidirectional character, a carriage return) is refused, never repaired. A text node carries each mark type at most once, `code` combines only with `link`, and a `codeBlock` holds text nodes without marks. A document over 5000 nodes or over `limits.body_chars` characters of text is exit 22 `body_too_large`. A prepared `--format adf` document must be strict JSON (duplicate keys, `NaN`, `Infinity`, an out-of-range number or nesting over 64 is exit 22 `invalid_value`), is input of at most 4 times `limits.body_chars` characters, and needs visible text (`empty_body`). Numbers must be JSON integers where an integer is allowed (`1.0` and `true` are refused by the code validator; a JSON Schema validator treats `1.0` as an integer, and lone surrogates and carriage returns in text are refused by the code only, so the code validator is the authority). The write side is stricter than the reader on purpose: it accepts only lowercase `http` and `https` links (`mailto` and uppercase schemes are refused on write, while the renderer is lenient on read), and card nodes (`inlineCard`, `blockCard`, `embedCard`) are refused as unknown nodes. The unique-mark and code-only-with-link rules in `schemas/adf.json` need a JSON Schema Draft 2019-09 or later validator (`maxContains`, `if`/`then`).

### Attribution

Every comment ticketctl posts carries the comment property `ticketctl.meta` with `{"v": 1, "actor_kind": "auto"|"human", "body_sha256": ..., "key_sha256"?: ...}` (the key part only when a dedupe key was given), written in the create request itself. ADF has no hidden text, so awkit-authored ticket comments are detected by this property on the user's own comments, a recorded deviation from the design guide's fixed marker. A comment posted through a transition `Comment` field carries no property and no dedupe. `comment-edit` rewrites the property with the edit (the `body_sha256` of the new body, the actor kind of the edit, the original `key_sha256`), and both `comment-edit` and `comment-delete` act only on a comment that has it and was authored by the authenticated account.

With `attribution.enabled` (default true) a comment or a created ticket's description starts with a first paragraph from `attribution.template` (plain text; no mentions or links), so no untrusted text can hide it. For an `auto:` actor it is mandatory and cannot be turned off; for a `human:` actor it is optional. The single template says "Drafted with AI assistance" for both actor kinds and so does not state that a human accepted the post (the audit `actor` and `actor_source` do). The actor string is the only test, and the claim is advisory (see [Trust boundary](#trust-boundary)). The line is part of the body the human confirmed. One rich-text rule for an `auto:` actor: the only rich-text write paths are a comment body and a created ticket's description (`--body-file`); a rich-text value from `--set` or `--field` is exit 22 `invalid_value` ("rich text by an automatic actor carries no attribution") on `update`, `create` and `transition` alike. An `auto:` create always gets the attribution paragraph as its first description paragraph, with the body after it when `--body-file` is given and alone when it is not; a `human:` create with no body omits the description. For a `human:` actor a rich-text `--set` or `--field` value is converted and checked by `validate_adf()` with no attribution.

## Invoking the provider

All HTTP goes through `src/ticketctl/gateway.py`, a stdlib client, under these invariants:

- `http.client` with one connection per write and an explicit `connect()` phase; a failure after the request was started is ambiguous; no connection reuse for writes.
- HTTP basic authentication with the site's email and token (the only place the token is placed, as the `Authorization` header; both values are stripped of surrounding whitespace), TLS verification on, and a fixed `User-Agent`. The token never appears in argv, the environment of a child, logs, audit, output or hook payloads.
- URLs are built only as `<site url> + path template`; an absolute URL from a response (`self`, `next`, attachment `content`) is never followed.
- Every 3xx is exit 12 `provider_changed`: no redirect is followed and credentials are never re-sent. On a write it is also `outcome_unknown` true, because a 303 may follow a processed POST.
- No `Accept-Encoding` header is sent, so there is no decompression; a response is read through a hard cap of 16 MiB (and `Content-Length` is checked), and a larger one is `provider_changed`.
- JSON parsing runs behind a string-aware, iterative depth guard at depth 400 (a deeper document is `provider_changed` for the whole response, a residual for rich-text searches and comment pages; default `search` fields and single-key reads are unaffected); the renderer's own depth budget of 50 gives per-ticket stubs below that.
- `--verbose` never sets an `http.client` debug level and never prints request headers.
- `HTTPS_PROXY`, `https_proxy` and `NO_PROXY` are honored through a CONNECT tunnel (TLS stays end to end); the destination is still only the configured host.
- Every attempt opens a fresh connection (`Connection: close`), reads included, and runs in a worker thread: the whole-command deadline is enforced by the main thread, which closes the socket, because a socket timeout does not bound a server that sends one byte at a time. A cancelled attempt that has not yet written a request byte never writes one. A certificate or hostname verification failure is not retried (it is deterministic): it is exit 12 `unavailable` with `retryable` false; other connection and TLS failures before the first byte are. A `Retry-After` is read only as whole seconds (an HTTP date is ignored and the backoff applies). A write that gets a 3xx is `provider_changed` with `outcome_unknown` true; a write whose response is oversized, malformed or too deep is `provider_changed` with `outcome_unknown` true, except after a 4xx status (nothing was applied), where it is false.
- Proxy values: only `http://[user:password@]host[:port]` is accepted (user information becomes `Proxy-Authorization` to the proxy only); any other form is exit 2 `invalid_config` naming the variable, never its value. A loopback `http` site is never proxied. `NO_PROXY` takes `*`, host names and domain suffixes (with or without a leading dot), `host:port`, IP addresses and CIDR ranges.

The provider API used is Jira Cloud REST v3 plus the agile API. Every endpoint ticketctl calls is in the table below.

### Jira endpoints

| Purpose | Endpoint |
|---|---|
| identity | `GET /rest/api/3/myself` |

## Reliability

- **Timeouts.** `timeouts.connect` (default 10 s) and `timeouts.read` (default 30 s) per site. The whole-command `--timeout` (default 120 s) covers provider work, the dedupe lock wait and the lag guard waits. The confirmation prompt and the `pre-` hook runs are excluded (the deadline does not run during them; hooks have their own timeouts), so the lock wait and the guard budget are the time left of the command deadline after them. The deadline is checked before each step. On expiry before any write was sent, or on a read, the command exits 12 `timeout`; once a write request may have been sent, expiry is `outcome_unknown` (or `partial` when an earlier step landed), never `timeout`.
- **Retries.** Reads retry up to 3 times (4 attempts) on a connection failure before a response and on 429, 502, 503 and 504; writes retry up to 2 times only on a connection or TLS failure before any request byte was sent and on 429, and never after any byte of the request may have been sent (the command then exits 12 `outcome_unknown`). Every sleep is `min(0.5 s * 2^n, 8 s)` with full jitter; a `Retry-After` replaces it and is honored when it is at most `limits.retry_after_max` and the remaining command time allows it, else the command ends 12 `rate_limited` with `retry_after_s` and no wait. All sleeping counts against `--timeout`. A body shorter than its `Content-Length` is a connection failure (retried on a read, ending 12 `unavailable`; on a write after the request was sent, a 2xx or 5xx answer with such a body is 12 `outcome_unknown`, and a 4xx answer stays that status's error), while a complete frame whose JSON is cut is `provider_changed` (`outcome_unknown` true on a write after a 2xx).
- **Re-running a write** is the caller's retry. A `comment-edit` re-run reports `unchanged` when the edit landed; a `comment-delete` re-run of a landed delete is exit 10 `not_found`. A `comment` or `create` re-run with the same `--dedupe-key` returns `already_posted` or `reused`; a `transition` or `update` re-run reports `unchanged` if it already happened ([Plan object](#plan-object), rule 1). `outcome_unknown` is retryable only by these recipes: it is `retryable: false` for a `comment` or `create` without a dedupe key, and its message says "re-run only with --dedupe-key". With a key, a `comment` re-run first looks the key up ([Dedupe](#dedupe)): a comment that landed is `already_posted`, so `outcome_unknown` is retryable.
- **Pacing.** When `X-RateLimit-Remaining` falls below 10% of `X-RateLimit-Limit`, ticketctl sleeps 1 s before the next request of the same command; the values appear in `--verbose` output and in the error envelope. There is no cross-process limiter.
- **Caps.** One `search` returns at most 500 tickets with pages of `min(remaining, 100)` and an explicit `fields` list (never `*all`, which silently returns 100 per page), at most 5 page requests plus the parse call and the count. `get` takes at most 50 keys, `comments --limit` and `changelog --limit` default to 50 (max 200), `changelog` reads at most 1000 entries in 20 requests, `get --comments N` at most 50, `sprints list --limit` defaults to 50 (max 500).
- **Version drift.** Unknown fields in a response are ignored, and the audit and log never depend on a response shape.

### HTTP status mapping

| Response | Exit and code |
|---|---|
| 404 on an endpoint whose path names an object (issue, comment, sprint, board, an issue's transitions and changelog) | 10 `not_found`; a missing, malformed or hidden key look identical, so the message says "missing or no permission" |
| 404 or any 410 on a collection endpoint (`search/jql`, `jql/parse`, `approximate-count`, `myself`, `field`, `priority`, `resolution`, the `board` listing) | 12 `provider_changed` |
| 401 | 12 `bad_credentials` |
| 403 on any call | 12 `forbidden` |
| 400 on a write | 12 `rejected`, the sanitized provider `errorMessages` and `errors` in `details` |
| 400 on `search/jql` | 22 `invalid_query` |
| 429 after retries | 12 `rate_limited` (see Retries above) |
| 502, 503, 504 and other 5xx after retries | on reads 12 `unavailable`, on writes 12 `outcome_unknown` |
| any other 4xx on a write (409, 413, 415, 422, ...) | 12 `rejected` (nothing applied) |
| 400 on `board/{id}/sprint` (a board without sprints) | 22 `invalid_value` with `details.option: board` |

The 410 rule of the collection row is for reads. On a write a 410 is "any other 4xx on a write": 12 `rejected`, nothing applied. A 404 on a write to a collection endpoint (`POST /issue`) is 12 `provider_changed`; a 404 on a write to an object path is 10 `not_found`, and the two sprint writes (`sprint/{id}/issue`, `backlog/issue`) map their 404 to 10 `not_found` as the sprint section says.

## Write flow

Every write (`transition`, `comment`, `comment-edit`, `comment-delete`, `create`, `update`, `sprint add|remove`) follows one order.

1. **Prepare** (no provider call). Argv grammars (exit 2), input files, Markdown conversion, `validate_adf()`, `secret_in_body`, size and `empty_body` (judged before the attribution paragraph is added), then the attribution paragraph is inserted and `attempt_id` is generated (16 random hex characters, used by every record and payload of the command).
2. **Resolve.** Select the site; for a write take a fresh `/myself` (this also refreshes `me.json`; reads use the cache) and apply `account_mismatch` (`auth_required` arises at the first call); read the ticket and the lists the action needs (`editmeta`, `createmeta`, the transitions); resolve names (`unknown_field`, `ambiguous_*`); run the dedupe lookup without a lock.
3. **Reduce and check.** Reduce the plan to its remaining steps ([Plan object](#plan-object), rule 1): none left is `unchanged` (exit 0, nothing else runs). Then `--if-status` (rule 4), then the provider-context checks for the steps that remain (`no_such_transition`, `ambiguous_transition`, `needs_resolution`, `missing_required_fields`, `not_editable`, `sprint_closed`), then build the plan and its hash and compare `--expect-plan` when given (rule 3; no comparison without it).
4. **`--dry-run`** prints the plan and stops. An empty `steps` is the plan of an `unchanged` run; a caller records no pending confirmation for it.
5. **Confirm** ([Human actions](#human-actions)). An interactive run shows the dialog and confirms once (default no). A non-interactive run without `--yes` exits 13 `confirmation_required` with nothing sent. The dialog tells the human that `pre-` hooks run after the answer; a decline is exit 20 `declined`.
6. **`pre-` hooks** run (see [Hooks](#hooks)); a veto exits 11, an escalation exits 13 `escalated`.
7. **Lock and fresh check.** With a dedupe key take the bucket lock ([Dedupe](#dedupe)), then re-read and rebuild the plan; for `comment` and `create` the fresh check is the dedupe lookup repeated under the lock. A hash difference from the held plan is exit 20 `stale_ticket` (rule 3), and no remaining steps is `unchanged`.
8. **Audit and send.** Append the `attempted` audit record, perform the provider calls in order, append the outcome record, release the lock, run the `post-` hook and print the result.

The order is fixed: the `pre-` hook runs after the confirmation, so a hook can veto or escalate a plan the human accepted; the human sees the veto as exit 11 with the hook's reason. The stale check stays after the hooks because it is the one nearest the write. `--yes` never overrides a refusal (exit 20).

- **No-ops never prompt.** A no-op (rule 1, including `already_posted` and `reused`) prompts nothing, runs no hook and writes no audit record; the request log still has its lines.
- **Post hooks.** A `post-` hook runs once, only when an `attempted` record was written, with `ok`, `failed`, `partial` or `unknown`; never for a refusal, a veto, `confirmation_required`, a no-op or an exit 22.
- **Gate decisions are not audited.** The audit holds only writes that reached the provider boundary (attempted plus outcome). A veto (11), an escalation (13), a stale or precondition refusal (20), a decline (20 `declined`) and `confirmation_required` write no audit record: the gate's own log is the record of its decision, and the envelope returns `decision_ids` and `hook` so the caller can record them. A `decision_id` is recorded in the audit records of the steps that follow.
- **`--dry-run` edges.** `--dry-run` takes precedence over `--yes` (see [Human actions](#human-actions)), ignores `--expect-plan`, does the reads (including dedupe lookups, so a hit prints a plan with no steps and a `dedupe_match`), reports a refusal with its exit code and envelope (an exit 20, 21 or 22 is shown, not hidden), runs no hook, takes no lock and writes no audit. "Writes nothing" means no provider write, no audit and no hook; cache refreshes and request log lines still happen.
- **Unexpected errors midway.** An exception that is not a ticketctl error while a step is being sent leaves the outcome unknown: the record is `unknown` and the failure is `outcome_unknown` (the message names the exception class, never its text), with the usual re-run rules; an interrupt (Ctrl-C) midway records `unknown`, runs the `post-` hook once with `unknown` (`partial` when an earlier step landed), and then propagates (exit 130). An interrupt anywhere else in the send (between two steps, between a request returning and its record, while an outcome record of any kind is being appended, while the result is built, or while the lock is released) sends nothing more and runs the hook once with what is known (`ok`, `failed`, `unknown`, or `partial` when a step landed; the steps not sent are listed `skipped`); a step that was not sent has no record. The hook runs only when an `attempted` append returned: an interrupt inside the very first `attempted` append (the record may or may not have been written) runs no hook.
- **Lock release.** A lock that fails to release after the outcome record is a stderr warning: the result or error of the write is still returned.
- **A landed create without a valid key.** When `create` landed but the provider's answer has no valid ticket key, the result prints `key` and `url` as null (the write happened; `attempt_id` and the post hook are intact).
- **Failure shape.** A failure prints the error envelope and nothing else (see [Result object](#result-object)); every failure after an `attempted` record carries `details.attempt_id`.

### Plan object

`schemas/cli/plan.json`: `action`, `site`, `key` (null for create), `actor`, `steps`, `changes`, `warnings`, `dedupe_key`, `dedupe_match` (the provider id or key of the object a dedupe lookup found, else null) and `plan_sha256`. The action names are `transition`, `comment`, `create`, `update`, `sprint_add`, `sprint_remove`, `comment_edit` and `comment_delete` (hooks use `sprint` for the two sprint actions; `comment_edit` and `comment_delete` have the hook families `comment-edit` and `comment-delete`; `plan.action` tells them apart). `steps` is an ordered list of provider calls in plain terms, `{kind: assign|transition|set_fields|add_comment|create|sprint_add|sprint_remove|edit_comment|delete_comment, ...}`, each a closed object with only the properties that apply to its kind: `account` (assign), `transition_id` and `to` (transition), `fields` (the field names of set_fields), `body_sha256` and `body_bytes` (add_comment, edit_comment and create; the bytes of the canonical JSON that was hashed), `comment_id` (edit_comment and delete_comment), `sprint` (the resolved sprint id of a sprint step), `project` and `type` (create). An empty `steps` array is `unchanged`.

`changes[].name` is `status`, `resolution`, `assignee`, `sprints`, `labels`, `title`, `description`, or a logical or `extra` field name; for `status`, `from` and `to` are `{name, category}`. A sprint remove lists its effect in `changes` too; a `comment` has no change entry (the body is in `steps` as hash and size), while `comment-edit` and `comment-delete` have one `comment` entry: `from` is the stored comment as Markdown and `to` the new text (null for a delete). `from` and `to` are untrusted JSON: for a rich-text field both are the rendered Markdown string (the text the confirmation dialog shows, the attribution paragraph included, never ADF), and in the hash input they are body hashes only. The `tc-` dedupe label is not listed.

`warnings` is an array of codes from one closed enum:

| Code | Meaning |
|---|---|
| `closed_ticket` | the ticket is in a done status |
| `assign_added` | the plan includes an assign step; it applies to a transition's assign step (including `assign_on_start`), and `update --assign` never emits it because the assign is the caller's named change |
| `other_sprints_dropped` | a sprint remove drops more than one open or future sprint |
| `sprint_moved` | a sprint add moves the ticket out of another sprint |
| `body_near_limit` | the body is over 90% of `limits.body_chars` |
| `duplicate_dedupe_matches` | several own tickets matched a create dedupe label |
| `assign_skipped` | `--assign` was not applied because the ticket has an assignee other than the requested target |
| `audit_incomplete` | a result only: an outcome record could not be written |
| `decision_ids_truncated` | a result only: hook decision ids beyond 16 in all (flag ids first) were dropped |

The plan is built, hashed and applied by one rule:

1. **Idempotency first.** After resolve, the plan is reduced to its remaining steps. A plan with none (the intended end state already holds) is `unchanged`: exit 0, no prompt, no hook, no audit record, before any hash comparison and whatever `--expect-plan` says, and before every check that only matters when a step remains. The end state per action: transition, the current status name equals the target (case-insensitive; with `--transition-id` the listed transition's `to` is compared, and an id absent from the live list is `no_such_transition`); update, canonical equality of every named field; sprint add and remove, membership ([`sprint add|remove KEY`](#sprint-addremove-key)); comment and create, a dedupe hit. Canonical comparison, for both this test and the facts: rich text as rendered Markdown (the converted ADF rendered by the reader's renderer, so re-serialization does not matter), numbers as decimals, dates as ISO strings, options by name, lists and labels as sorted sets, users by account id.
2. **The hash.** `plan_sha256` is the sha256 of the canonical JSON (sorted keys, no whitespace, UTF-8) of `{v: 1, action, site, key (the project for create), intent, facts}`. `intent` is what the caller asked for, resolved: the target status and the resolved transition id (not the typed `--to`), the resolution, the effective assign target (`me`, `none`, an account id or null, after `--assign` and `assign_on_start`, whether or not a step results), field names with value hashes, body hashes, labels, the resolved sprint id and the dedupe key; for `create`, also the trimmed title, the issue type and the parent key (so `plan_sha256` covers every input of `create`). `facts` is only what the plan reads: for a transition, the current status name and the assignee when that assignee is neither none, nor the resolved `me`, nor the requested assign target; for an update, the current values of the fields it changes (for label operations, whether each named label is present); for sprint add and remove, the ticket's current open and future sprint ids; for comment and create, none. Steps are derived from intent plus facts and are not hashed, so an assign step that appears or disappears between plan and apply runs as the plan said (it was in the confirmed intent). The actor is not hashed: a body that carries the attribution line already differs in its hash.
3. **Two comparisons.** The hash is compared when the plan is built (against `--expect-plan`, before any hook runs) and again after the hooks, from a fresh read just before the first write (write-flow step 7). A difference is exit 20 `stale_ticket` with `details.plan`; a fresh read that now shows no remaining steps is `unchanged` (rule 1).
4. **`--if-status`.** `transition` accepts `--if-status <name>`: when the ticket's current status is not that name (case-insensitive) the command exits 20 `precondition_failed` (`details.current_status`, `details.expected_status`). It is evaluated after rule 1 and before the provider-context checks and the hash, and is the only precondition flag (the assignee guard is in the hash).

### Result object

`schemas/cli/result.json`, printed on exit 0: `{action, site, key, url, changed, result, steps, already_posted, reused, comment_id, attempt_id, decision_ids, warnings}`. `result` is `ok` (a provider write happened) or `unchanged` (nothing was sent: already in the target state, `already_posted`, `reused`); `changed` is true when a provider write landed (`ok`, and `partial` inside its envelope); `already_posted` and `reused` are required booleans; `comment_id` is null except for `comment` (and then it is the existing id for `already_posted`); `url` is the ticket's browse URL; `attempt_id` is null when nothing was audited (`unchanged`); `warnings` holds the plan warnings that apply. A no-op has `steps: []` and `decision_ids` holding the flag ids; `reused` carries the existing key. Each step has `status` `done`, `skipped` or `failed`; `skipped` means in the plan but not run because an earlier step failed.

`partial` is printed only inside `details.result` of an exit 12 envelope with `code: partial`. A command whose earlier step landed and a later one failed (definitely, or unknown) exits 12 `partial`; `details.result` holds the full result object (`result: partial`, the per-step statuses, `attempt_id`, `decision_ids`), and the failing step's own error is copied into `retryable`, `retry_after_s` and `outcome_unknown` of the envelope (`outcome_unknown: true` when the failing step is unknown) and into `result.steps[i].code`. A failure with nothing applied keeps its own code (`rejected`, `outcome_unknown`, ...) and has no `details.result`. Nothing is rolled back.

The three `result` vocabularies are different on purpose:

| Where | Values |
|---|---|
| result object | `ok`, `unchanged` (and `partial` only inside an envelope) |
| audit record, per provider call | `attempted`, `ok`, `failed`, `partial`, `unknown` |
| post-hook payload, per command | `ok`, `failed`, `partial`, `unknown` |

### Transition order

`transition KEY --to <status>` resolves the transition from the live list by target status name, case-insensitively. No match is exit 20 `no_such_transition` listing the available targets; several matches exit 21 `ambiguous_transition`; these checks run only while a step remains (a re-run after a landed transition is `unchanged`, never exit 20). `--transition-id <id>` bypasses the name match. A ticket already in the target status is `unchanged`, unless `--assign` was given and the ticket is unassigned: the assign step alone then remains (result action `transition`, one step). If the target's category is `done`, a resolution is required while a step remains: `--resolution <name>` or `sites.<site>.transitions.default_resolution` (exit 22 `needs_resolution` otherwise), validated against the transition's allowed values (and, when they are not listed, against the provider's resolution list). `--resolution` with a non-done target is exit 22 `invalid_value`, and is ignored for an `unchanged` result. A done ticket reached by another route (workflow automation) with no resolution is `unchanged`: ticketctl never backfills a resolution in 0.x. Transitions out of a done status are not special-cased: the live list decides and `closed_ticket` warns. The provider accepts a done transition with no resolution and leaves it empty, so ticketctl never sends one without it. A transition whose required fields are not supplied is exit 22 `missing_required_fields` with `details.required_fields`, as for `create`.

`--assign me|<account>` on `transition` means "assign if unassigned": the assign step is in the plan exactly when the ticket is unassigned at plan time and either `--assign` was given, or `sites.<site>.transitions.assign_on_start: me` is set, the target's category is not `done` and a transition step remains. When `--assign` was given and the ticket already has an assignee the step is skipped and the plan warns `assign_skipped`. The step is explicit, shown in the dry-run and audited. Otherwise the transition is sent as is and the plan holds no assign step. The requirement for an assignee is a workflow validator that neither the transitions list nor `editmeta` shows (a Sub-task's done transition may need one), so it cannot be pre-checked: a provider 400 on the transition call is exit 12 `rejected` with nothing applied, and `details.reason_hint: needs_assignee` is added when the ticket was unassigned and the plan had no assign step (decided from the plan facts, never from the message text). The assign and the transition are two calls and are not atomic; a failure of the second is exit 12 `partial`. Other required transition fields are passed with `--field name=value` and validated against the transition's field list; a sub-task transition that needs a parent takes `--field parent=KEY`.

The remaining rules of the command, where the paragraphs above leave room:

- `--assign` takes `me` or an account id; `none` and any other spelling of `me` or `none` exit 2 `invalid_argument` (an assign that only acts on a free ticket cannot unassign). The plan warns `assign_skipped` only when the ticket has an assignee other than the requested target (a ticket already assigned to the target needs nothing and says nothing), so a re-run after the assign landed does not warn.
- The checks run in this order: the live ticket and, while a transition step can remain, the transition list are read; a `--transition-id` that the list lacks is exit 20 `no_such_transition` even for a no-op; a ticket already in the target is `unchanged` (or has the assign step alone); then `--if-status`; then `no_such_transition` or `ambiguous_transition` for `--to` (`details.available_targets`, and `details.candidates` as `id: name`), `needs_resolution` (`details.candidates` lists the allowed resolutions when the transition lists them), an invalid resolution (exit 22 `invalid_value` with `details.candidates`; a resolution is matched case-insensitively and sent in the provider's spelling) and `missing_required_fields` (the required fields of the transition that `--field` did not give, `resolution` excluded). `--resolution` and `--field` are ignored for an `unchanged` result and for a plan that holds only the assign step.
- The candidate lists of these errors (`available_targets`, the `candidates` of `ambiguous_transition`, `needs_resolution` and an invalid resolution) are sorted and capped at 50 entries.
- `--field` names resolve against the transition's own field list and the values are converted once; a field of schema type `comment` is posted as `update.comment` (an `add` operation), every other field goes in `fields`. Their `changes` entries have `from: null` (the current values are not read) and are named by the typed logical or `extra` name, else by the field's display name; their value hashes are in the intent.
- The intent holds the resolved target status name, the resolved transition id (null when no step sends one), the canonical resolution, the effective assign target and the `--field` value hashes; the facts hold the lower-cased current status and an assignee only when it is neither `me` nor the requested target.

### Dedupe

`comment` and `create` accept `--dedupe-key <string>` (a short identifier chosen by the caller, grammar in [Identifiers](#identifiers), never secret); `--yes` requires it ([Human actions](#human-actions)). The provider has no idempotency, so ticketctl records the key on the object it creates. The lookup in resolve is lock-free and feeds the plan and the dry-run, so a hit gives an empty plan (`unchanged`) and a human is never asked to confirm a post that will be skipped; under the lock (write-flow step 7) it is repeated as the fresh check.

- **Comment.** The key is stored in the `ticketctl.meta` property ([Attribution](#attribution)) of the comment as `key_sha256`, the sha256 of the key string alone (UTF-8), beside `body_sha256` of the final ADF. The lookup lists the ticket's comments newest first with `expand=properties`, keeps those whose `author.accountId` equals the fresh `/myself` account of the write flow (not `me.jira`), parses the property defensively (only an object with `v == 1` and a 64-hex `key_sha256` counts; anything else is "no marker") and scans at most 1000 comments. The key found with the same `body_sha256` is `already_posted` (exit 0); with a different one it is exit 20 `already_exists` with `details.existing_id`, and nothing is posted (a re-run under a different attribution template or setting also finds a different hash: the safe direction). If the key is not found and more comments exist, the command exits 12 `lookup_incomplete` rather than assuming absence; it is not retryable, an automatic caller reports it and only a human may post without a key. The lookup runs on the same comment list as `comments --own` and reads the stored hashes, never the comment text, so an edited comment still matches by its stored body hash and a deleted one is gone (the key is then posted again). A hit whose property has a valid `key_sha256` but no valid `body_sha256` counts as another body. "Cannot prove absence" is any scan that is truncated (more than 1000 comments, a page that ended early, no usable count), that dropped a comment (an unreadable or repeated id, an unreadable date) or in which a comment's properties or body could not be read; with no hit the scan is repeated once (a concurrent comment between two pages can repeat an id) and, if the second scan cannot prove absence either, it is `lookup_incomplete`; with a hit the hit stands. No lag guard is needed: the comment list is read-your-writes. A comment posted without a key is never deduplicated.
- **Create.** The key is stored as a label `tc-<first 16 hex characters of sha256(site \0 project \0 key)>`. The label and the `--label` values go in `fields.labels` of the create request, so `create` is always one provider call and `partial` cannot occur on it. `labels` is exempt from the `unknown_field` and `not_editable` pre-check against `editmeta` and `createmeta` (the create body accepts it although createmeta does not list it). A 400 with a `labels` error from a site's create screen is exit 12 `rejected` with the provider's `details.field_errors`, and the message says to create without a dedupe key, which only an interactive human can do, because `--yes` requires a key (there is no fallback for automated callers). The lookup searches `project = "<P>" AND labels = "tc-..." AND reporter = "<account id from /myself>"`. The found ticket's issue type and exact title must match the plan (the title is trimmed of surrounding whitespace before it is hashed, sent and compared; sha256 compared): a match is `reused` and nothing else runs, a mismatch is exit 20 `already_exists` with `details.existing_key`. A key is bound to type and title only: a reused key with a different description, parent or labels is `reused`. A keyless create runs no lookup and takes no lock, so two identical keyless runs, or a human re-run after a timeout that raced a landed write, can create a duplicate; only a keyed create is deduplicated. Several own matches (a race) return the oldest by key with the warning `duplicate_dedupe_matches`. Issue and comment properties are not searchable, so they are never a lookup key for tickets. A `--label` matching `^tc-[0-9a-f]{16}$` (the reserved pattern) is exit 22 `invalid_value` on `create` and `update`.
- **Lock.** The lock is taken at write-flow step 7 (after the hooks, never across the prompt), held to the outcome record and released before the `post-` hook runs; its descriptor is close-on-exec, so no hook or child can keep it. Locks are a fixed set of 256 bucket files `state/locks/<first two hex of sha256(site \0 project-or-key \0 dedupe key)>` taken with `flock`, waiting up to the command timeout, then exit 12 `unavailable` with `reason: locked`; a collision only serializes unrelated writers and nothing accumulates. On release the holder updates the file's modification time and leaves the file one byte long (a file that was never released has size 0, and its modification time, the creation, does not start the quick re-run). The lock is not re-entrant: taking a bucket the same thread holds is an internal error, never a wait.
- **Lag guard.** The label index lags a create (about a second for a label added by update; the lag after a create was not measured). A `create` lookup under the lock that finds nothing is therefore repeated before it concludes "absent" in two cases. When the lock file was modified within the last 5 s (a waiting run or a quick re-run on one host) it repeats once after 2 s. When the tail of `audit.jsonl` (the last 1 MiB of it, read by the guard itself without the audit lock) holds a create record with the same `target.site` and `inputs.dedupe_key` and a `ts` within the last 120 s that is `attempted` with no outcome record, or whose outcome is `unknown` or `ok` (the retry after `outcome_unknown`), it repeats every 5 s for up to 60 s from that record's `ts`, bounded by `--timeout`, and a hit ends it at once. Per attempt only the record with the highest `seq` counts; a `ts` in the future is clamped to now plus 60 s; a lock file with more than one link is refused (`state_type`). A wait the guard needs but that does not fit in the time left of `--timeout` (a wait strictly longer than the time left) is exit 12 `timeout` with nothing sent, never a conclusion of "absent". A re-run from another host is a residual risk. Comments need no guard (their list is read-your-writes).

The caller owns key hygiene: a new body needs a new key.

## Commands

All commands accept the [global flags](#global-flags) where meaningful. Every command that outputs data supports `--json`; with `--json` anywhere in argv an argparse failure also prints the error envelope (the parser is wrapped and the message is sanitized). Write-only flags (`--yes`, `--dry-run`, `--expect-plan`, `--actor`, `--decision-id`, `--override-escalation`, `--hook`, `--if-status`) on a read command exit 2 `invalid_argument`. A flag that fails argparse (type, choice, required, mutual exclusion) and every shared flag grammar (actor, decision id, dedupe key, numeric ids, durations, integers) exit 2 `invalid_argument`; violations of "exactly one of" rules and `--verbose` with `--quiet` exit 2 `invalid_combination`. Values that feed site selection or the provider path (ticket keys, project keys, site names, browse URLs) and values judged with config, provider or object context exit 22.

### `whoami`

Prints `{site, account_id, display_name, source}` for the selected site: the `/myself` account (cached in `me.json`, or fresh with `--refresh`), `source` being `cache` or `provider`. Schema `schemas/cli/whoami.json`.

### `get KEY...`

Reads up to 50 distinct keys (a duplicate is read once; the 51st distinct key exits 22 `invalid_value`); every key's grammar is validated up front and any failure exits 22 `invalid_key`; all keys must select one site. Options: `--fields a,b`, `--comments N`, `--include-adf`. Output is `{tickets, errors}`: `tickets` in input order, `errors` a list of `{key, error}` where `error` is the full envelope body for that key (`not_found`, `forbidden`, any other). Every key readable: exit 0. Some succeeded: exit 0 with `errors` non-empty (a consumer must read `errors`). None succeeded: the exit of the first error in input order (10 when all were not found) with the error envelope alone and `details.errors` holding the per-key list (the shape of `get.json`). A single key keeps the single-key behavior (a missing ticket exits 10 with the envelope). Reads are issued with concurrency 4 and order is restored before printing. `--comments N` takes 1 to 50 (any other integer, negative or huge included, exits 22 `invalid_value`; text that is not an integer exits 2 `invalid_argument`) and applies when `comments` is among the printed properties (the default read, or `--fields` naming it). A comment object is kept only when its id, `created` and `updated` are readable (else it is dropped and `comments` or `comments.invalid_id` is named in `incomplete`: an `updated` guessed from `created` would claim the text was never edited); `ticketctl.meta` is read on the caller's own comments only, and `authored_by_ticketctl` is true whenever the property is present on an own comment, whatever its content (and, failing closed, when an own comment's `properties` is missing or not a list; see [Comment object](#comment-object)). A failure of a ticket's comment call is that key's error. Two typed keys that resolve to one moved ticket print it twice, each with its own `requested_key`. For a single key the error is the plain envelope (no `details.errors`). Schema `schemas/cli/get.json`.

### `search`

The filter is a query form plus structured flags. The query form is one of `--query <name>` (a named query from `sites.<site>.queries.<name>`, a JQL string in the user's own config; an unknown name is exit 22 `invalid_value` naming the query and the site), `--jql-file <path>|-` or a short `--jql <text>` for humans; the last two are raw queries and untrusted. A named query combines with the structured flags and a raw query stands alone, as described in [Search compilation](#search-compilation). The structured flags are:

| Flag | Meaning | Repeats |
|---|---|---|
| `--project` | project key | OR |
| `--status`, `--status-category new\|indeterminate\|done` | status name, category (`new` compiles to `"To Do"`, `indeterminate` to `"In Progress"`, `done` to `"Done"`, the `statusCategory` names) | OR |
| `--assignee me\|none\|<account>` | `--assignee none --assignee me` is the "unassigned or mine" pool | OR |
| `--sprint open\|future\|<id>` | sprint selector | OR |
| `--label` | label | AND (all present) |
| `--parent <key>`, `--type`, `--priority` | parent key, issue type, priority | OR |
| `--key` | a batch of keys (`key in (...)`) | OR |
| `--not-status`, `--not-label`, `--not-parent`, `--not-type` | exclusions; each excludes every listed value | all values excluded |
| `--updated-since`, `--created-since` | a time ([Search compilation](#search-compilation)) | last wins |
| `--text <string>` or `--text-file <path>\|-` | one clause `text ~ "<phrase>"` (a quoted phrase, see [Search compilation](#search-compilation)), at most 200 characters, never from argv alone; with `--text-file` the CLI strips exactly one trailing newline, and any other newline inside the text is exit 22 `invalid_value` | one |

Different flags are ANDed. Everything else (components, due-date filters, board filters) is a named query in the user's own config or a raw query that stands alone; ticketctl's quoting guarantee covers the structured flags only, and board-based pools are named queries (`filter = <id>`). `--board` on `search` is a 1.x candidate.

Also `--order-by <field>[:asc|:desc]` (including `rank`), `--limit N` (default 50, at most 500, at least 1; `--limit 0` only with `--count`; else exit 22 `invalid_value`), `--fields`, `--count` and `--cursor <token>`. The cursor is opaque (`base64url` of `{v: 1, site, jql_sha256, page_token}`) and valid only for the same site and the same compiled JQL. A cursor over 4096 bytes, one that does not decode (the nesting depth is checked iteratively, at most 4, before parsing, and every decoding failure is caught), whose `v` is not 1, whose `site` or `jql_sha256` differs from this command's, or whose `page_token` is not a printable ASCII string of at most 1024 characters exits 22 `cursor_invalid`, never exit 1; a token the provider rejected exits 22 `cursor_expired` ("restart without --cursor"). `--updated-since` plus `--cursor` are the documented incremental pool refresh; a ticket leaving a pool is not reported (the consumer re-reads claimed keys with `get`). There is no `--comments` on `search`. Schema `schemas/cli/search.json`.

The run order is: offline rules (exactly-one rules, the raw query combination rule, `--limit`, the `--fields` vocabulary, `missing_option`), the cursor's shape, site selection (`--site`, else `--project` and `--key` values, else the default), compilation, the cursor's site and `jql_sha256` against this command's, the strict parse check, `--count`, then the pages. A cursor is the unpadded `base64url` text `encode` printed, and a padded spelling is accepted only in its canonical form (a non-canonical spelling is `cursor_invalid`); the JSON inside must be the exact text `encode` prints (sorted keys, no spaces, ASCII), so a re-spelled document is `cursor_invalid` too. The parse check runs on every run, with a cursor too. `--limit 0 --count` sends no search request and prints `tickets: []` with `truncated` true when the count is above 0 and `next` null (there is no page token to hand out). The page loop stops at `--limit` tickets or 5 page requests; a page with no issues but a `nextPageToken` is followed and counts as a request. A provider answer that makes the loop unsafe is exit 12 `provider_changed`: more issues than asked for, a missing `issues` list, a `nextPageToken` that is repeated or is not printable ASCII of 1 to 1024 characters. A failure on any page, also after earlier pages, is that failure's error and no ticket is printed (all or nothing; the caller re-runs, with the cursor of an earlier run when it kept one). A 400 on the first search request that carried `--cursor` is `cursor_expired`, since the same query already passed the parse check; a 400 on any other page is `invalid_query`. A key printed twice by the provider across pages is printed once, and a result with no usable key is skipped with a warning on stderr.

#### Search compilation

A raw query (`--jql-file`, `--jql`) is never split, wrapped or combined: it cannot be given with a structured filter flag, `--text`, `--text-file`, `--query` or `--order-by` (exit 2 `invalid_combination`), it is validated by the parse endpoint and runs alone. Only a named query (the user's own config) combines with the structured flags. It is split at its last top-level `ORDER BY` by a small scanner that skips double- and single-quoted strings with backslash escapes (a backslash outside a string is exit 22 `invalid_query`, because the scanner and Jira could disagree on where a string starts; `ORDER BY` inside a longer word, ASCII or not, is not the keyword); the tail after the keyword is the query's order clause. As defense in depth the scanner first proves the where-part balanced (quote-aware, parenthesis depth never negative, ending at zero, no open quote), else exit 22 `invalid_query` ("unbalanced parentheses or quote"), because a where-part such as `status = Open) OR (project = X` would escape the AND-ed flags; the scanner is a copy of Jira's lexer rules, and Jira's own lexing is not verified (see [Residual risks](#residual-risks)). Any JQL text (a raw query, a named query or the compiled whole) longer than 4096 characters exits 22 `invalid_query` before the scanner runs, which also bounds its cost; `ORDER BY` is matched by a compiled pattern at a position, never on a slice. Only then is the where-part wrapped in parentheses, each structured flag becomes one parenthesized clause, all are joined with `AND`, and the order clause is `--order-by` when given (it replaces the query's), else the query's. The result is always validated through the provider's parse endpoint with strict validation: a mis-split, a syntax error, an unknown field, status, option value or function exits 22 `invalid_query` naming the offending token, because the provider otherwise answers a semantic error with an empty result. An empty result is therefore always a real zero. A 400 from `search/jql` (for example "unbounded JQL queries are not allowed") is also `invalid_query`, with the provider's sanitized text in `details.errorMessages`.

Each structured flag compiles to exactly one clause or an error: exit 22 for a value that fails its check, but exit 2 `invalid_argument` for an `--assignee` account id or a `--sprint` id that fails its grammar (shared flag grammars), except that an `--assignee` or `--sprint` value over 256 characters is exit 22 `invalid_value`, because the length check runs first. Quoted strings are double-quoted with `\` then `"` escaped; a value with a control, format, private-use, unassigned or line-separator character, with one of the invisible characters the sanitizer replaces by its explicit list (such as U+034F, U+2800, U+3164, U+FE00 to U+FE0F, U+FFFC), or longer than 256 characters is `invalid_value` (the length is judged first, before any grammar or rendering). Unquoted tokens have grammars:

| Token | Grammar and compilation |
|---|---|
| duration | `^[0-9]{1,4}[mhdw]$`, compiled `-<n><unit>` |
| timestamp | the time grammar below |
| sprint selector | `open` (compiled `openSprints()`), `future` (`futureSprints()`), or digits (the id) |
| `--status-category` | `new`, `indeterminate` or `done`, compiled to the quoted category name |
| `--assignee` | `me` is `currentUser()`, `none` is `EMPTY`, an account id is quoted and matched against `account_id` |
| `--text` | the text has `\` then `"` escaped and is wrapped in inner double quotes, and the whole is escaped and quoted again: a Lucene phrase inside the JQL string, so `[ ] { } ( ) ^ ~ * ? : + - & \| !` in a title are literal. It is a tokenized, punctuation-insensitive phrase match, so results can be near matches and the caller compares titles when it needs equality |
| `--order-by` | `<field>[:asc\|:desc]` (the direction in lower case), field `^[A-Za-z][A-Za-z0-9_]{0,63}$` (JQL clause names, `rank` included) or a logical field name mapped to its clause. The logical names are the ten of [Field mapping](#field-mapping) plus `updated` and `created`; a logical name with no mapped clause (and no built-in one), or whose mapped clause name is not a usable JQL clause name, exits 22 `unknown_field`. Logical names are matched case-insensitively (`Epic` and `Due_Date` are `epic` and `due_date`); any other field keeps its case. A site's `extra` names map too, except that `updated` and `created` always mean the built-in clauses, whatever a config maps |

One time grammar serves `--updated-since`, `--created-since`, `comments --since`, `changelog --since` and `export --since`: an RFC 3339 timestamp with `Z` or an offset, a date `YYYY-MM-DD`, or a duration `<n>m|h|d|w`. In `search`, timestamps compile into the JQL minute format in the site user's time zone, taken from `/myself.timeZone` (stored in `me.json`; absolute JQL dates are read in that zone), rounded down to the minute; durations compile to relative JQL. For `comments` and `export` a bare date means 00:00 UTC. In `search`, a bare date is midnight in that zone (absolute JQL dates are read there, so it is not converted), and a value that fits no form of the grammar exits 22 `invalid_value`. A timestamp needs the zone: an absent, malformed or unknown zone is exit 22 `invalid_value`, and so are the database entries that are not zones (`localtime`, `posixrules`, `Factory`). `UTC` and `Etc/UTC` are built in; every other zone is read from the system time zone database (the platform's zoneinfo files; there is no `tzdata` dependency), and a system without that database fails with "system time zone database not found or zone unknown". A timestamp exactly at a daylight-saving fall-back fold compiles to the same minute string on either side of it, so an incremental refresh should overlap the previous window by at least an hour. Every flag takes at most 512 values (exit 22 `invalid_value`), a search with no query and no filter flag exits 2 `missing_option`, and a named query or raw query that holds a control, format, line-separator or non-ASCII space character (other than tab, CR and LF) exits 22 `invalid_query`. The sprint states are `future`, `active` and `closed`; the selectors are `open` (the `active` state), `future` (search only), `next` (`sprint add` only) or an id.

### `comments KEY`

Lists comments (`--limit` default 50, max 200; `--since <ts>`, which filters on `created`; `--newest-first`; `--own`, which needs the resolved account), paged with `startAt`. The scan reads at most 1000 comments (the dedupe cap) and sorts locally rather than trusting the provider's order within the window: it reads the whole window (up to 20 page requests) and sorts it itself, although on a thread above 1000 comments the window itself follows the provider's `orderBy` (not yet verified live), so `--limit N` with the default order returns the oldest N matching comments of the window, with `--newest-first` the newest N (`get --comments N` is the newest N, oldest first). Output `{key, site, items, total, truncated}`: `total` is the number of comments on the ticket before the `--since` and `--own` filters; `truncated` is true when the limit or the cap stopped the scan with more matching comments beyond, when a page ended the scan early (an empty page or one that is not a comment list) while `total` says more comments remain, and when a comment was dropped (an unreadable id or time) or a repeated comment id was skipped, because the listing is then not the whole thread. `--since` keeps the comments created at or after the time (inclusive, a duration counts back from now) and is judged before any request; it filters inside the same 1000-comment window, so on a thread above 1000 comments the default order sees only the oldest 1000 (`truncated` is true) and a caller who wants recent comments passes `--newest-first`, which applies the filter from the newest end; `--limit` outside 1 to 200 is exit 22 `invalid_value`. The scan also stops after 20 page requests, and `truncated` is then true unless the count shows nothing is left; a provider that gives no usable `total` makes `total` the number of comments scanned and `truncated` true. The schema has no `incomplete` list, so a comment that was dropped or a part that could not be read is also one warning line on stderr (`--quiet` suppresses it, the `truncated` flag stays). `key` is the requested key in canonical form. Schema `schemas/cli/comments.json`.

### `changelog KEY`

Lists the change history of one ticket (`--limit` default 50, max 200, exit 22 `invalid_value` outside it; `--since <ts>`, which filters on the entry's `created`, inclusive, in the one time grammar and judged before any request; `--field <name>`, repeatable (at most 20), which keeps only the items of that field, matched case-insensitively and exactly against the printed `field` name, and drops an entry that has none left (the filter runs before the 200-item cap of an entry, so the cap counts matching items only, and a cut of matching items names `changelog.truncated` and sets `truncated`; what an entry loses, such as an unreadable item or an `items` value that is not a list, is still named in `incomplete` and sets `truncated` when the entry is dropped, because the lost part might have matched; a `--field` of more than 20 values, a blank value or a value over 256 characters is exit 22 `invalid_value`); `--newest-first`). The order is oldest first by default and newest first with `--newest-first`, as for `comments`; the entries are sorted locally by `created` (the id breaks a tie) whatever order the provider sent, and the first `--limit` of the filtered, ordered entries are printed. It reads `GET /issue/{key}/changelog` page after page (`startAt`, `maxResults=100`): at most 1000 entries are looked at, at most 20 page requests are made and the loop ends at the first empty page. A history longer than 1000 entries is read from its newest end for `--newest-first` (the window starts at `total` minus the smaller of 1000 and 19 pages of the length the first page had, so a provider that pages at 50 gets a window of 950) and from its oldest end otherwise, which assumes the provider lists the oldest entry first (not yet verified live); `--since` filters inside the window like `comments --since`. Output `{key, site, items, total, truncated, incomplete}`: `total` is the provider's entry count before the filters (never less than the entries seen); `truncated` is true when the limit or a cap stopped the scan with more entries unread or matching, when a page ended the scan early while `total` says more remain, when the provider gave no usable `total` (a page with `isLast: true` and no `total` ends the list without a mark and is not truncated, while a missing `total` without `isLast` names `changelog` and sets `truncated`), and when an entry was dropped or a repeated id skipped; `incomplete` is the sorted list of the parts that could not be read completely (`changelog` for an entry, item or value that was dropped or unreadable, a page that is not a list or no usable `total`; `changelog.invalid_id` for an identifier outside its grammar; `changelog.truncated` for a text or list cut at its cap or a read bound (1000 entries, 20 requests) that stopped the scan with entries unread; an empty list when nothing was lost, and a `--limit` alone adds nothing) and is always printed, and when it is not empty the command also writes one warning line on stderr (`--quiet` suppresses it). `key` is the requested key in canonical form; a moved ticket is read under the old key as `comments` does (the endpoint resolves it). It is a read: no lock, no audit record and no hook, and a missing, malformed or hidden ticket is exit 10 `not_found` and a forbidden one exit 12 `forbidden`, as for `get` and `comments` (see [HTTP status mapping](#http-status-mapping)). The history of a ticket can hold a person's earlier text, so every value is untrusted. Schema `schemas/cli/changelog.json`.

### `transitions KEY`

Lists the transitions available now, with required fields: `{key, site, transitions}`. A transition with no readable id, name or target status is left out, `required_fields` lists the fields whose `required` is `true` (a field with no readable name is `unknown field`, and no provider field id is printed), `has_screen` is `true` when the provider did not say, and a field whose `required` is present but not a boolean is left out; at most 200 required fields are listed (optional fields do not count). All omissions together are one warning line on stderr (`--quiet` suppresses it; the schema has no `incomplete` list). A name that holds a provider custom field id shows the marker `<id>` in its place. Schema `schemas/cli/transitions.json`.

### `sprints`

`sprints list [--state future|active|closed] [--board <id|name>] [--limit N]`, `sprints show <id>` and `sprints resolve open|next`. Without a key the board is `--board`, else `sites.<site>.board`, else the scrum boards of `--project`, else of the site's only project, else exit 2 `missing_option`. `--board <name>` is matched case-insensitively and exactly against the boards of the site (at most 5 pages of 50); a digits-only value is an id; several matches, or several scrum boards for a derived project board, exit 21 `ambiguous_board`; no board is exit 10 `not_found` with `details.option: board`. When the name search (or the project's board listing) was cut off by the 5-page cap and exactly one board matched, a second board may lie beyond: the command exits 12 `lookup_incomplete` (not retryable) and asks for `--board <id>`; several matches are still exit 21, and no match is still exit 10. A 400 on `/board/{id}/sprint` (a board without sprints, for example a kanban board named by the user) is exit 22 `invalid_value` with `details.option: board`. `list` returns the provider's order by ascending id within the pages read, reading pages of 50 until `--limit` is reached (default 50, max 500), as `{site, sprints}`; a consumer wanting the latest uses `--state`. `show` returns `{site, sprint}` and needs no board (`--project` only selects the site). A sprint that lacks an id, a name that is not blank (a zero-width name shows as a visible `<U+200B>`-style marker and is kept), a state or an origin board id of at least 1 is left out of a listing with one warning line on stderr that `--quiet` suppresses (`provider_changed` for `show`), a dropped sprint being reported nowhere else because the schema has no `incomplete` list; a custom field id in a sprint or board name shows as `<id>`, the state filter is applied again on the client, and a listing reads at most 20 pages. Names are matched with `str.lower` on both sides; the boards of a name search are all those of the site, and only `scrum` boards count for a project. `sprints resolve open|next [--board <id|name>] [--project P]` is the read-only form of the target rule of [`sprint add`](#sprint-addremove-key): it prints the one sprint that `sprint add KEY --sprint open|next` would pick, as `{site, sprint}` (the object `sprints show` prints, with `start`, `end` and `board`), so a caller does not copy the two rules. It is one code path with `sprint add`: `open` is the board's one `active` sprint (several active, up to the 20 read, exit 21 `ambiguous_sprint` with `details.candidates`; none exit 10 `not_found` with `details.option: sprint`), `next` is the `future` sprint with the earliest non-null `start`, else the lowest id (none exit 10 `not_found`), a listing that was cut off exits 12 `lookup_incomplete` (for `next` also one that reaches the 500 cap), and a listed sprint that cannot be read exits 12 `provider_changed`. The board is resolved as for `list`: `--board`, else `sites.<site>.board`, else the scrum boards of `--project`, else of the site's only project (exit 2 `missing_option`, 21 `ambiguous_board`, 10 `not_found` or 12 `lookup_incomplete` as above); the only difference from `sprint add` is that there is no ticket, so the project is `--project` (or the site's only project) and never a ticket's. The selector is `open` or `next` only (a sprint id is `sprints show`; any other word exits 2 `invalid_argument`). The command takes no lock, writes no audit record and runs no hook; names are sanitized as for `show`. Schemas `schemas/cli/sprints-list.json`, `schemas/cli/sprints-show.json` and `schemas/cli/sprints-resolve.json` (the same shape as `show`).

### `fields`

`fields list` prints the discovered fields (the one command that prints provider field ids) with their schema and the logical mapping; `fields check` validates the configured mappings against them; `fields refresh` replaces the cache; `fields types` lists the issue types a project can create. `fields check` prints its problems (`missing`, `ambiguous` and `type_mismatch`, the last for a mapped field whose schema is not one the logical field accepts: `estimate` a number, `sprint` an array of sprint objects, `acceptance_criteria` a string or rich text, `due_date` a date) as data and exits 0 whenever it ran (an empty list when the mappings are sound); an offline invalid config exits 2. `fields list` prints each field with the logical name it is the unique match of (null otherwise) and the `mapping` of every logical name to its unique field (null when missing, ambiguous or absent), sorted by id; `fields refresh` always fetches and replaces the cache (a failed fetch, or an empty field list, is exit 12 `provider_changed` and keeps the old one); a cache that cannot be written, including `cache_ttl: 0` (no cache), only warns or writes nothing, and `refreshed: true` means the fetch succeeded. Schemas `schemas/cli/fields-list.json`, `schemas/cli/fields-check.json`, `schemas/cli/fields-refresh.json` and `schemas/cli/fields-types.json`.

`fields types [--project <key>] [--type <name>]` is the read-only discovery route of `create`: it replaces probing through `create --dry-run`. It prints `{site, project, types}` where `types` (sorted by name) is `[{id, name, subtask, required_fields}]`, read from the createmeta of the project with the same paging caps and answer shapes as `create`. Without `--type`, `required_fields` is `null` for every type (not read; one request series for the type list only). With `--type <name>` (the matching of `create --type`: an exact name, else the one case-insensitive match; an unknown or ambiguous name is exit 22 `invalid_value` with `details.candidates`) only that type is listed and `required_fields` is `[{name, kind, allowed_values?}]`, the shape of `details.required_fields` of `missing_required_fields`, under the same rules as `create`'s check: a field is listed when the provider says `required: true` and no default value, except `summary`, `project`, `issuetype` and `reporter` (ticketctl fills them in), and `parent`. A field that `create` fills from `--body-file`, `--assign` or `--label` is listed, because the type still requires it. `parent` is never listed, as under `create`: whether a parent is needed, and which parents fit, is the provider's rule (a sub-task type that needs one rejects a create without it); `subtask` is the provider's own flag (`null` when it did not say): `true` means `create` needs `--parent`, while `false` does not promise that `create` needs no parent, because the provider decides. Without `--project` the site's only `projects` entry is used (after the site was selected by the other rules), else exit 2 `missing_option`; a project that is missing or hidden is exit 10 `not_found`; a createmeta answer that is unusable is exit 12 `provider_changed`. The command only reads: it takes no lock, writes no audit record, and reads createmeta fresh on every run (it is not cached). Type names are provider text, sanitized and capped, and no provider field id is printed in a field name (a type named like a field id is printed as the provider names it, as under `create`'s candidates). Schema `schemas/cli/fields-types.json`.

### `sites`

Prints the configured sites and their `projects`; `sites resolve KEY_OR_URL` (a KEY or a browse URL) prints `{key, site, rule}`, where `rule` is `site_flag`, `url`, `project`, `default_site` or `only_site` (see [Site selection](#site-selection)). `sites resolve --project P` takes a project key instead of a ticket key or URL (exactly one of the two, else exit 2 `usage`: `missing_option` for neither, which was an argparse error before `--project` existed, and `invalid_combination` for both or for `--project` given twice) and prints the same object with `key` null, because no ticket is named: `key` is a ticket key for a KEY or URL argument and always null for `--project`; the project is the one the caller passed. The site and `rule` follow the same table as a key of that project: `--site` wins, then the sites whose `projects` hold P (one selects it, rule `project`), then `default_site`, then the only site; several sites claiming P exit 21 `ambiguous_site` with `details.candidates`, a malformed project key exits 22 `invalid_key`, and zero configured sites exit 2 `no_sites`. A project no site claims is not an error (rule `default_site` or `only_site`, as for a key); a consumer that needs the project to be claimed checks `rule` is `project`. Offline: no network and no credentials are read. Schemas `schemas/cli/sites.json` and `schemas/cli/sites-resolve.json`.

### `validate`

`validate` checks the configuration offline (shape only, plus the loader checks under [Config](#config); exit 2 on invalid config, naming the key) and prints `{valid, probe, warnings, read_only?, sites?}` (`read_only` is `true` and present only when [read-only mode](#read-only-mode) is on), where `warnings` is a list of advisory problems of the configuration itself (an ignored nested `TICKETCTL_` variable, for example; empty when there is nothing to say) that a consumer shows as a warning. A configuration with no site is exit 2 `no_sites`. `validate --probe` (with `--site`, only that site; every site otherwise) also makes read-only calls: it authenticates, compares the account with any configured expectation, runs the same routine as `fields check` and parses every named query, and prints the problems per site under `sites[].problems` (an `account_mismatch` problem has no `logical`; each named query is compiled as `search --query` compiles it and then sent to the parse endpoint, one request per query, and listed under `sites[].queries` with `valid` and its `error`, so a query the provider rejects is data, not a failure, while a non-2xx or wrong-shaped answer of the parse endpoint (which is documented to answer 200) is exit 12 `provider_changed` and only the strings of its `errors` mark a query invalid; the field list is fetched fresh and a site's credentials or a provider failure is an error naming the site); it exits 0 whenever it ran, `valid` meaning only that the configuration is valid. Schema `schemas/cli/validate.json`.

### `transition KEY`

See [Transition order](#transition-order). Exactly one of `--to <status>` and `--transition-id`; `--resolution`; `--assign me|<account>` (assigns only an unassigned ticket; plan warning `assign_skipped` otherwise); `--field name=value|@file|-` (repeatable, the grammar of `--set`; `resolution` and the other dedicated names are refused with exit 2 `invalid_combination`); `--if-status <name>`. See [Value grammar](#value-grammar).

### `comment KEY`

Exactly one of `--body <text>` and `--body-file <path>|-`; `--format markdown|adf` (`adf` only with `--body-file`); `--dedupe-key`. The comment is posted as the authenticated account.

The body is converted to ADF (Markdown, or ADF from `--body-file` with `--format adf`), gets the attribution paragraph, and is refused locally when empty (`empty_body`), over `limits.body_chars` (`body_too_large`) or when it holds a configured token (`secret_in_body`); no wiki markup is ever sent. The one `add_comment` step posts the body and the `ticketctl.meta` property in the same request. The plan has no `changes` entry and no facts, so a ticket that changed since the plan never makes it stale; it warns `closed_ticket` for a done ticket (a closed ticket accepts comments) and `body_near_limit` above 90% of `limits.body_chars`. The result carries `comment_id`; `already_posted` is set by the dedupe lookup ([Dedupe](#dedupe)): with `--dedupe-key` the ticket's comments are searched for the key before anything is posted, and `--yes --expect-plan` requires a key (the engine rule).

### `comment-edit KEY ID`

Replaces the body of one comment that ticketctl posted. `ID` is the comment's numeric id (the `comment_id` of a `comment` result or `id` of `comments`; a value outside the numeric-id grammar is exit 2 `invalid_argument`). Exactly one of `--body <text>` and `--body-file <path>|-`; `--format markdown|adf` (`adf` only with `--body-file`). There is no `--dedupe-key`: the command is idempotent by itself, and `--yes --expect-plan` needs no key. It is its own command rather than a subcommand of `comment` because `comment KEY` takes a positional key; `comment` itself is unchanged.

- **Which comments.** Only a comment that this tool can tie to itself: the author is the authenticated account (`own`) and the comment carries a valid `ticketctl.meta` property ([Attribution](#attribution): `v` 1, an `actor_kind` of `auto` or `human`, a 64-hex `body_sha256`). Any other comment (another account's, an own comment posted in the web UI or by another tool, an own comment whose property is missing, malformed, of another version or read as absent) is exit 20 `not_ticketctl_comment` and nothing is sent. The marker is advisory: it is a property that its author can write, so the author test and the provider's own permission checks (a 403 is exit 12 `forbidden`) are the gates. A comment whose text was edited outside ticketctl after the post still counts (its stored body no longer hashes to the property, and the plan shows the stored text under `from`).
- **Restricted comments.** A comment with a visibility restriction (a group or role) is exit 20 `restricted_comment`: the update request carries no visibility, whether the provider keeps, drops or widens the restriction then is unverified, and a restricted comment must never become public by an edit. `comment-delete` has no such rule.
- **Body.** The new body goes through the same preparation as `comment` (Markdown or ADF, the attribution paragraph by the actor rules, `empty_body`, `body_too_large`, `secret_in_body`, validation of the final ADF): the body replaces the old one as a whole, the attribution paragraph included, and it is a new final text the human confirms. The one `edit_comment` step sends `PUT /rest/api/3/issue/{key}/comment/{id}` with `{body, properties: [ticketctl.meta]}`, so the property is rewritten in the same request and always describes the stored body: `body_sha256` is the hash of the new ADF, `actor_kind` is the actor of the edit, and `key_sha256` of the original post, when there was one, is kept (so a keyed re-run of `comment` finds the edited comment and reports `already_exists`, never a second post). The notify-users option is never sent.
- **Plan.** The comment is read first (`GET .../comment/{id}?expand=properties`). Idempotency first: a new body whose ADF hash equals the stored body's is `unchanged` (exit 0, no step, no confirmation, hook or audit record; `comment_id` is set). The hash intent is the comment id and the new body hash and the fact is the hash of the stored ADF, so a comment changed since the plan is exit 20 `stale_ticket`; a ticket change is not. `changes` has one `comment` entry (`from` the stored text, `to` the new text, both Markdown), and the plan warns `body_near_limit` above 90% of `limits.body_chars`. A 404 on the comment or the ticket is exit 10 `not_found`; an answer that is not a comment of that id is exit 12 `provider_changed`.
- **Result and hooks.** `comment_id` is the edited id. The hooks are `pre-comment-edit` and `post-comment-edit` (the `comment` hooks do not run): the payload is that of `comment` without `dedupe_key` and with `plan.comment_id`; `provider_ids` of the post hook is the comment id. The audit action is `comment_edit` and its step kind `edit_comment`. Schema `schemas/cli/comment-edit.json`.
- **Retry.** `outcome_unknown` is retryable: re-plan with `--dry-run` (a landed edit shows no step) and apply again.

### `comment-delete KEY ID`

Deletes one comment that ticketctl posted, by the same rule as `comment-edit` (own and carrying a valid `ticketctl.meta`; anything else is exit 20 `not_ticketctl_comment`, nothing is sent; a restricted comment may be deleted). It takes no body. Deletion cannot be undone, so it has no shortcut: the confirmation is the one of every write (a dialog for a human, `--yes --expect-plan` for a driven caller, which needs no dedupe key) and the dialog shows the stored text as the `from` of the plan's one `comment` change (`to` is null). The one `delete_comment` step sends `DELETE /rest/api/3/issue/{key}/comment/{id}`. The hash intent is the comment id and the fact is the hash of the stored ADF, so a comment edited since the plan is exit 20 `stale_ticket`. The result carries the deleted id as `comment_id`. A comment that is already gone is exit 10 `not_found` (it cannot be told from one that never existed), so a re-run after `outcome_unknown` that finds it missing means the delete landed or the id is wrong: check with `comments`. The hooks are `pre-comment-delete` and `post-comment-delete`, the audit action `comment_delete` with step kind `delete_comment`. Schema `schemas/cli/comment-delete.json`.

### `create`

`--project <key>` (or the site's only `projects` entry, used only after the site was selected by the other rules; with several entries exit 2 `missing_option`), `--type <name>` (validated against createmeta; an unknown type is exit 22 `invalid_value` with the valid types in `details.candidates`), `--title <text>` or `--title-file` (at most 255 characters, else exit 22 `invalid_value`), `--body-file` only (there is no short `--body`, and `--set description` is refused), `--parent <key>` (a sub-task needs it), `--assign me|none|<account>` (part of the create body, so there is no assign step; without it the provider default applies; `none` sends an explicit unassigned value), `--label` (repeatable; no whitespace, at most 255 characters; a reserved dedupe pattern is refused, see [Dedupe](#dedupe)), `--set name=value|@file|-` (repeatable; priority, estimate and due date go through it with logical names; see [Value grammar](#value-grammar)), `--dedupe-key`. `create` is one provider call and has no `--sprint`: run `sprint add` on the returned key. Required fields that are not supplied exit 22 `missing_required_fields` with `details.required_fields` (`[{name, kind, allowed_values?}]`; fields that have a default value or that ticketctl supplies are not missing); [`fields types`](#fields) is the read-only discovery route (`create --dry-run` with the type and without the values also shows the missing fields, as a refusal). The result carries the new key and `reused: true` when a dedupe match was found. The type name matches case-insensitively (an exact match wins; several matches exit 22 `invalid_value` with the candidates) and is sent by its createmeta id. `parent` is never reported as a missing required field: whether a parent is needed, and which parents fit, is the provider's rule, and its 400 is exit 12 `rejected` with the field errors (naming `parent`) in `details.field_errors`. A required field of the screen that ticketctl supplies (`summary`, `project`, `issuetype`, `reporter`, and `description`, `assignee` and `labels` when given or implied) or that has a default (`hasDefaultValue`) is not missing. A landed create sends no `ticketctl.meta` property (properties of tickets are not searchable and the dedupe label carries the key). Createmeta reads: a 404 on either createmeta endpoint is exit 10 `not_found`; the type list is read at 200 entries per page and the field list likewise, at most 25 pages each (more is exit 12 `provider_changed`), and the lists end at `isLast: true`, at an integer `total`, at an empty page or, when the provider says neither, at a page shorter than its page size. The type list is accepted under `issueTypes` or `values` and the field list under `fields` or `values`, as a list (each field named by `fieldId`) or an object keyed by field id; more than 1000 types or 10,000 fields is `provider_changed`. The dedupe lookup refuses (`provider_changed`) a found key of another project or with more than 18 digits, and counts a ticket listed twice once.

### `update KEY`

`--title <text>` or `--title-file` (at most 255 characters), `--assign me|none|<account>` (always assigns; `none` unassigns; never the provider's automatic assignment), `--add-label`, `--remove-label` (the same label in both exits 22 `invalid_value`; no whitespace, at most 255 characters; a reserved dedupe pattern is refused), `--set name=value|@file|-` (repeatable; `description` is set with `--set description=@file`, there is no `--body-file` on `update`; see [Value grammar](#value-grammar)). With no change flag the command exits 2 (`reason: missing_option`). Values are converted by the field's schema; an unknown or non-editable field exits 22 `unknown_field` or `not_editable` before anything is sent. Setting a value the ticket already has is `unchanged`. An update with several change kinds runs `set_fields` first (the step that can fail on field values) and `assign` second, so a failure of the second is exit 12 `partial`; label operations ride in the same `set_fields` request as the other fields, using the provider's `update` verbs. Only what differs from the ticket becomes part of the request (a label already present is not added again, an absent one is not removed), and the notify-users option is never sent. The plan names a change `title`, `labels`, `assignee`, `description`, the logical or `extra` name of a mapped field, else the field's display name (a provider field id inside it shows as `<id>`); `--assign` is a change whose `from` and `to` are account ids (`to` null for `none`). A rich-text value (`--set description=@file`) carries no attribution paragraph and needs a `human:` actor (for an `auto:` actor it is exit 22 `invalid_value`). The hash facts of a changed field are its value before the change (a label operation: whether the label is present), so after an exit 12 `partial` whose `set_fields` landed a re-run reports a new plan hash for the remaining `assign` step: a held `--expect-plan` is exit 20 `stale_ticket` carrying that one-step plan, and a re-run without `--expect-plan` (or with the new hash) sends only `assign`. A caller retries a multi-step update after exit 12 by taking the plan from the `stale_ticket` `details.plan` or by re-running without `--expect-plan`. A moved ticket is written and reported under its canonical key.

### `sprint add|remove KEY`

Takes exactly one key; callers loop. One plan, one result, one audit pair and one hook pair per command; multi-key writes are a 1.x candidate.

- `sprint add KEY --sprint open|next|<id>`: already in that sprint is `unchanged`; in another future or active sprint the plan shows `from` and `to` and warns `sprint_moved` (the plan assumes the provider moves the ticket out of its sprint rather than adding it to a second one; unverified live); a closed target exits 20 `sprint_closed`; a provider refusal (a sub-task, a ticket outside the board) is `rejected`. `open` is the board's one `active` sprint (several active exit 21 `ambiguous_sprint`; none exits 10 `not_found` with `details.option: sprint`); `next` is the future sprint with the earliest non-null `start`, else the lowest id (never ambiguous; none exits 10 `not_found` with `details.option: sprint`). A board listing that was cut off exits 12 `lookup_incomplete` for `open` and `next` alike, and for `next` only, a future-sprint listing that reaches the 500 cap does too (`open` with 20 or more active sprints is instead exit 21 `ambiguous_sprint`); a listed sprint that cannot be read exits 12 `provider_changed` for both (no guess is made from an incomplete listing). A 404 on the sprint write is exit 10 `not_found` (sprint or ticket missing or hidden). Sprint membership for the plan, the hash facts and the end-state test means the ticket's `future` and `active` sprints only; closed sprints are history and ignored.
- `sprint remove KEY` takes no `--sprint` (exit 2 `invalid_combination` if given): it moves the ticket to the backlog, which for the verified case (one active sprint) removed it from that sprint; the membership counted is `future` and `active`. The plan lists the open and future sprints dropped in `changes` and warns `other_sprints_dropped` when more than one; a ticket with no open or future sprint is `unchanged`. A 404 on the backlog write is exit 10 `not_found` (ticket missing or hidden). Moving a ticket out of a closed sprint is not claimed (unverified).
- Plan and facts: the plan's `changes` holds one `sprints` entry whose `from` and `to` are lists of `"<id>: <name>"` strings (the names are untrusted and sanitized; a remove has `to: []`). The step of an add carries `sprint` (the resolved id), the step of a remove carries none. The hash intent is the resolved sprint id (add) or the backlog move (remove) and the facts are the ticket's open and future sprint ids, so an `open` that now resolves to another sprint, or a changed membership, is `stale_ticket`, while a renamed sprint or an edited ticket is not. `sprint_closed` is judged only while a step remains (a dry run shows it). The sprint hooks carry `sprints` as the target (add) or the dropped sprints (remove). A sprint value on the ticket that cannot be read is exit 12 `provider_changed`, never "no sprint": only an explicit null or an empty list means no sprint, an absent field, a non-list, an entry without a numeric id, a state or (unless it is closed) a name, or one sprint listed in two states is unreadable. `sprint add` needs `--sprint` (exit 2 `missing_option`).
- Board: `--board <id|name>` (also on `sprint add`; it is only used to resolve `open` and `next`, an explicit sprint id and `sprint remove` need no board, and there `--board` is accepted and ignored: only its grammar is checked), else `sites.<site>.board`, else the scrum boards the ticket's project is on. One is used; none exits 10 `not_found` with `details.option: board`; several, or a name matching several boards, exit 21 `ambiguous_board` (matching as under [`sprints`](#sprints)).

### `export`

Prints audit records as JSON lines on stdout: `--since <ts>` (bare dates are UTC) and `--after-seq <n>` (ANDed), `--to <path>`. With `--to` the file is created per [Input files](#input-files) and an existing file exits 20 `already_exists`; without it nothing is created. `--json` has no extra effect. A line that is not a JSON object with `v == 1` is skipped with one warning; other lines are not validated against the schema, so records written by a later minor version pass. Each record carries `seq`: a `v == 1` line whose `seq` is not an integer from 1 to 2**53 is skipped too. Also skipped and counted in the same warning: a line that is not valid UTF-8 or not JSON (a raw NUL byte included, and `NaN` or an infinity anywhere), a record nested deeper than 12 levels or with more than 100000 nodes, and, with `--since`, a record whose `ts` is missing or is not a timestamp (a record excluded by `--after-seq` is not counted). With `--since`, a `ts` is compared by instant, so a fraction of a second or an offset form is read as the time it names. With `--to` the records go to the file and stdout stays empty. The file is read without the flock up to the size seen when it was opened, so records appended meanwhile wait for the next run (`--after-seq`); a last line with no newline (a torn tail or a write in flight), of any length, is neither printed nor warned about, and a terminated line over 64 KiB is skipped. Every string is sanitized and scrubbed again on output (a number that equals a token value is written as the string `<redacted>`), stdout and `--to` receive the same bytes, and a configuration that does not load never stops an export. If stdout cannot be written the export stops: a closed pipe exits 141 with nothing printed, any other write error exits 1 `internal`. Schema `schemas/cli/export.json` (each line is one audit record).

## Global flags

`--json`, `--config <path>`, `--site <name>`, `--verbose`, `--quiet`, `--timeout <duration>` (the duration grammar, 1 s to 24 h), `--dry-run` (writes), `--yes` (writes; always needs `--expect-plan`), `--expect-plan <sha256>`, `--actor <string>`, `--decision-id <id>` (repeatable), `--override-escalation[=<scope>]` (human-only, see [Human actions](#human-actions); the scope is `ticketctl`), `--hook <name>=<command>` (repeatable, in addition to configured hooks), `--version`. `--quiet` suppresses non-error stderr (not the confirmation dialog); `--verbose` prints extra diagnostics (rate limits, retries) on stderr and never headers; both together exit 2 `invalid_combination`. A value that can carry untrusted text is accepted as a file or stdin, never only as argv (design guide §4.1): bodies, titles, JQL, text filters and `--set` rich-text values. At most one `-` source per command (exit 2 `stdin_conflict`). `--config <file>` loads only that file (no drop-ins). A time setting takes the duration grammar under [Config](#config).

`--help`, `-h` and `--version` always print plain text to stdout and exit 0, whatever `--json` says.

### Input files

One reader serves every file argument (`--body-file`, `--title-file`, `--jql-file`, `--text-file`, `@file`). It opens with `O_RDONLY|O_NONBLOCK|O_NOFOLLOW|O_CLOEXEC`, requires `fstat` to show a regular file (so a FIFO never blocks), then clears non-blocking; it refuses a path under `/proc`, `/sys` or `/dev`, judged on the opened descriptor's resolved path (`/proc/self/fd/N` on Linux, `F_GETPATH` on macOS, `realpath` as the fallback; stdin `-` is the exception). It reads at most `4 * limits.body_chars + 1` bytes for bodies and 1 MiB for the others, and decodes strict UTF-8. A failure is exit 22 `invalid_file`. Any other file the user can read is readable this way (see [Trust boundary](#trust-boundary)). Before any send, an outbound body, title, JQL, label or field value that contains the exact value of any configured token variable (a value of at least 8 characters) is exit 22 `secret_in_body`; the message never echoes the value or its position. `export --to` opens with `O_WRONLY|O_CREAT|O_EXCL|O_NOFOLLOW` and mode 0600 and requires the parent to be a directory owned by the caller. The cache writes (temporary file plus rename) and the state directory use `O_NOFOLLOW` and ownership checks. A driven caller can still create new files with `export --to`.

## Exit codes

One table of exit, `code`, `reason` and the caller's action. `retryable` is true for `timeout`, `unavailable`, `rate_limited` and `outcome_unknown` (the last only by the re-run recipes under [Reliability](#reliability): false for a `comment` or `create` without a dedupe key; `provider_changed` with `outcome_unknown` true, such as a 2xx whose body cannot be used, is never retryable: the provider contract changed, so check the ticket before any re-run), false for everything else, `lookup_incomplete` included; `partial` copies the failing step's value. `retry_after_s` is set for `rate_limited` and `unavailable` when the provider sent `Retry-After`. `reason` is required (non-null) for exits 2, 20 and 22, and null otherwise except where listed.

| Exit | `code` | `reason` | Caller action |
|---|---|---|---|
| 0 | none | none | success, including `unchanged`, `already_posted` and `reused` |
| 1 | `internal` | `audit_failed` when the `attempted` append failed and nothing was sent, `hooks_unavailable` when a hook is configured or given with `--hook` and the shell that runs hooks (`/bin/sh`) is not executable (nothing was sent), else null | report; do not retry blindly |
| 2 | `usage` | `human_only`, `yes_requires_expect_plan`, `dedupe_key_required`, `stdin_conflict`, `invalid_combination`, `missing_option`, `invalid_argument` | fix the invocation |
| 2 | `invalid_config` | `config_invalid`, `no_sites`, `account_mismatch` | fix the config |
| 10 | `not_found` | null (a ticket, sprint or board) | the object is missing or hidden |
| 11 | `vetoed` | null (the hook in `details`) | report the hook's reason |
| 12 | `auth_required`, `bad_credentials`, `forbidden`, `rejected`, `unavailable` (reason `locked` possible), `timeout`, `outcome_unknown`, `rate_limited`, `provider_changed`, `partial`, `lookup_incomplete` | null | by code: `outcome_unknown` re-run per Reliability (find the `unknown` audit record by `details.attempt_id`); `partial` read `details.result`; `rejected` read `details.errorMessages`, `details.field_errors` and any `reason_hint`; `lookup_incomplete` report, only a human may post without a key |
| 13 | `confirmation_required`, `escalated` | null | store `details.plan`, `plan_sha256`, `decision_ids` and the hook; a human confirms later |
| 20 | `stale_ticket`, `precondition_failed`, `no_such_transition`, `sprint_closed`, `already_exists`, `declined`, `read_only`, `not_ticketctl_comment`, `restricted_comment` | equal to the code | `stale_ticket`: re-plan with `--dry-run`, never retry as is; `not_ticketctl_comment` and `restricted_comment`: the comment cannot be changed through ticketctl (see [`comment-edit`](#comment-edit-key-id)), stop; `already_exists`: pick a new key or keep the existing id (for `export --to`, choose a new path); `declined`: the human said no, stop and record nothing; `read_only`: read-only mode is on, stop (never retry; the config or environment must change, and that is the operator's decision, not the caller's) |
| 21 | `ambiguous_site`, `ambiguous_field`, `ambiguous_transition`, `ambiguous_board`, `ambiguous_sprint` | null (candidates in `details.candidates`) | name one candidate |
| 22 | `invalid_request` | `invalid_query`, `unknown_field`, `not_editable`, `invalid_value`, `needs_resolution`, `missing_required_fields`, `node_not_allowed`, `body_too_large`, `empty_body`, `unknown_site`, `invalid_key`, `mixed_sites`, `invalid_file`, `secret_in_body`, `cursor_invalid`, `cursor_expired` | the input failed ticketctl's own validation; fix it |

`needs_resolution` is exit 22: the plan needs one more input. Exit 2 is for a flag or shared flag grammar that fails (argparse, actor, decision id, dedupe key, numeric ids, account ids, durations, integers); exit 22 is for a ticket, project or site identifier, a browse URL, or a value judged with config, provider or object context.

Exit 130 is not a table row: it means the process was interrupted by SIGINT before any result, and it prints one line `ticketctl: interrupted` on stderr and no envelope.

## Output by exit code

With `--json`, exit 0 prints the command's object: for the write commands one of `schemas/cli/transition.json`, `schemas/cli/comment.json`, `schemas/cli/comment-edit.json`, `schemas/cli/comment-delete.json`, `schemas/cli/create.json`, `schemas/cli/update.json`, `schemas/cli/sprint-add.json` and `schemas/cli/sprint-remove.json`, each a result or, with `--dry-run`, a plan; a failure prints the error envelope on stdout (and the message on stderr). Without `--json`, human text goes to stdout and errors to stderr. The stderr message has no schema.

### Error envelope

`schemas/cli/error.json`: `{"error": {"code", "message", "reason", "retryable", "retry_after_s", "outcome_unknown", "site", "key", "details"}}`. `details` keys are named once; which appear depends on the code: `attempt_id` (on every failure after an `attempted` audit record was written), `candidates` (also the valid issue types for an unknown `--type`), `available_targets`, `field`, `fields`, `option`, `token`, `required_fields`, `plan`, `result`, `hook`, `escalated_hooks`, `hook_stderr`, `decision_ids`, `existing_id`, `existing_key`, `current_status`, `expected_status`, `reason_hint`, `field_errors`, `errors`, `errorMessages`, `rate_limit`, `token_env`. `confirmation_required`, `escalated`, `vetoed` and `declined` carry `details.plan` (the full plan with `plan_sha256`); the first three also carry `details.decision_ids` (every id returned by hooks and given with `--decision-id`), and the last two of those also carry `details.hook` (the hook that escalated or vetoed; `details.escalated_hooks` lists several) and `details.hook_stderr` (sanitized, at most 4096 bytes, untrusted). The caller stores the hash and later passes `--yes --expect-plan` with `--override-escalation=ticketctl` for an escalation; no second dry-run is needed. `stale_ticket` carries the new plan. `details.errorMessages` and `details.field_errors` are the provider's (sanitized, untrusted); `details.errors` is only the `get` per-key list of `{key, error}` with the full error body, the shape of `get.json`. The provider answers errors in three body shapes (`errorMessages` with `errors`, `{"error": ...}` and plain text) and the gateway maps all of them to this envelope. `details.reason_hint` is `needs_assignee` (see [Transition order](#transition-order)).

## Hooks

Per kind of write, one `pre-` and one `post-` hook: `pre-transition`, `post-transition`, `pre-comment`, `post-comment`, `pre-comment-edit`, `post-comment-edit`, `pre-comment-delete`, `post-comment-delete`, `pre-create`, `post-create`, `pre-update`, `post-update` (including assign and label changes), `pre-sprint`, `post-sprint`. Reads have no hooks. Hooks follow the design guide §8 (own process group, JSON on stdin, no templates, timeout default 30 s). Hooks run in the caller's working directory.

- **Order.** Configured hooks run in list order, then `--hook` ones. Exit 0 continues. Exit 13 escalates and the remaining hooks still run (a later veto wins). Any other non-zero exit vetoes at once (later hooks do not run): exit 11, the hook's sanitized stderr in `details.hook_stderr`. A timeout is a veto and the hook's process group is signaled.
- **`pre-`** runs at write-flow step 6, after the plan and the confirmation and before the first provider write (not for `--dry-run`). stdout may be a JSON object with `decision_id` (a string or a list): every id returned, also by an escalating or vetoing hook, is returned in `details.decision_ids` of that exit and recorded in the audit records of the steps that follow. An id that fails the decision-id grammar, or one beyond 16 in all, is dropped with one stderr warning and is never a veto. `--override-escalation=ticketctl` overrides the escalation of every hook ticketctl ran, never a veto ([Human actions](#human-actions)). Hook stdout is not validated. The `attempt_id` in a `pre-` payload is provisional: no audit record follows a veto, a stale refusal or a decline.
- **`post-`** runs after the outcome record and the lock release, once per attempted command (see [Write flow](#write-flow)), best-effort, never fatal, `async: true` optional. There is no event id and no at-least-once delivery.
- **Payload** (`schemas/hooks/<hook>.json`): `tool`, `hook`, `object_type` (`ticket`), `object_id` (the key; null for `pre-create` and for a `post-create` that created nothing, which includes an `unknown` outcome without a key: the key is never guessed), `site`, `project` (the key prefix or the create project), `actor`, `attempt_id`, `decision_ids`, `plan`, `body`. `plan` is per hook family: `action`, `steps` (the kinds), `current_status` and `target_status` (a transition has both; create has neither; the other actions have only `current_status`), `fields_changed` (names), `resolution`, `assign` (transition and update: the assign step's target `me`, `none` or an account id, null when the plan has no assign step), `plan_sha256`, `dedupe_key`, `comment_id` (the `comment-edit` and `comment-delete` families), as the family needs. `body` is the array of `{sha256, bytes}`, one for every rich-text value (the body or description first, then `--set` and `--field` values in argv order). Ticket hooks (all but create) add `ticket` `{type, subtask, status, priority, assignee_account_id, assignee_is_me}` (names and ids only: status, type and priority names are workflow configuration, not ticket text). Sprint hooks add `sprints`, a non-empty list of `{id, state}` (the target for add, the dropped open and future sprints for remove). Create hooks add `create` `{type, parent, assign}` (`parent` is a key or null). `post-` hooks add `result` (`ok`, `failed`, `partial` or `unknown`: `partial` when any earlier step landed and a later one failed or is unknown, else the single outcome), `error` (`{code, reason}` or null), `steps` (`[{kind, status}]`), `provider_ids` (the comment id, the created ticket id, else the ticket id) and `changed` (true for `ok` and for every `partial`, because a step landed; false for `failed`; null only for `unknown`). There is no `repo`, so every ticketctl gate decision is recorded in gatectl's scope `*` and per-project policy uses the `project` field in rules; there is no `labels`. Payloads carry no ticket text: no title, description, comment or label text; a policy that needs text reads it with `get`. The payload is built from the resolve read (write-flow steps 2 and 3) and may predate a long confirmation.
- **Execution.** Each hook runs as `/bin/sh -c <cmd>` (argv list, no other shell layer) in its own session and process group, in the caller's working directory, with the payload on stdin as ASCII JSON. stdout and stderr are each read up to 64 KiB (the rest is dropped, so a chatty hook never blocks); stdout is read for `decision_id` only when it holds one JSON object within that cap, and a hook that prints anything else simply returned no id (a pre- hook is never vetoed for its stdout). A non-zero exit, a death by signal, a hook that cannot be started and a timeout all veto a `pre-` hook (fail closed); a timeout sends SIGTERM to the hook's group, then SIGKILL after 2 s. Whatever the exit, the group is SIGKILLed before the shell is reaped, so no process a hook left behind outlives it (a hook that must outlive the command starts its own session). The signal goes only to the group the tool created, recorded at launch (the unreaped leader keeps the group id from being reused). A `post-` hook failure, timeout or crash is one stderr warning (no stderr relay) and never changes the exit code; every configured `post-` hook runs. An `async: true` hook is started detached with its payload on an anonymous file and no timeout is enforced on it. A `--hook` command is at most 4096 characters, one line of printable characters (a tab is allowed; every other control, format, surrogate, private-use, unassigned, line and paragraph separator character is refused, exit 2 `invalid_argument`). The resolve read supplies the ticket facts of the payload; a payload that lacks one is refused (`internal`) and a `pre-` hook that cannot be built never runs the write.
- **Environment.** The tool's environment minus every configured `token_env` and `email_env` variable (of every site) and minus any variable whose value contains a configured token value (an `Authorization`-style or proxy value that embeds it included; tokens of at least 8 characters), plus `TICKETCTL_HOOK`, `TICKETCTL_ID` (equal to `object_id`: empty only for `pre-create` and for a `post-create` that created nothing) and `TICKETCTL_OBJECT_TYPE=ticket`.

## Config

`~/.config/ticketctl/config.yaml`, drop-ins `config.d/*.yaml`, `--config` overrides (design guide §5). Schema [`schemas/config.json`](../schemas/config.json); every key is documented with its default in `config.example.yaml`. Invalid config fails fast naming the key. The default location reads `config.yaml` then `config.d/*.yaml` in lexical order: maps merge, `hooks` lists append, other lists replace; the merged document is validated. `--config <file>` loads only that file. The configuration directory is `$XDG_CONFIG_HOME/ticketctl` when `XDG_CONFIG_HOME` is an absolute path (a relative value is ignored), else `$HOME/.config/ticketctl`. Config files and the `config.d` directory must be owned by the current user or root and not world-writable; a file is read with a 1 MiB cap and at most 64 drop-ins are read (more is an error). A `config.d` entry named `*.yaml` that is not a regular file (a directory, say) is refused, while other entries (other extensions, dotfiles, subdirectories) are skipped. A missing default `config.yaml` is an empty configuration, and zero sites is an error only for a command that needs a site (`no_sites`). An explicit `null` is refused for every key with an error naming the key path (omit the key instead), so a drop-in cannot unset a value and `email: null` never counts as unset. YAML 1.1 number forms (`010`, `0x10`, `0b11`, `1_0`, `1:30`, `+5`) are not integers here: only decimal integers without leading zeros (and a negative, which fails its range) are numbers, so those forms (and `-0`) stay strings: they fail the duration grammars and are read as board names for `board`. A site `board` given as an integer is `1` to `999999999999999999` (the numeric id grammar), and a board name must not be blank. The `url` scheme and host are lower-cased by the loader, and [`schemas/config.json`](../schemas/config.json) describes that normalized form.

One duration grammar serves every time setting (config, flags, hook timeouts): `<integer>(ms|s|m|h|d)` or a bare integer meaning seconds. `0` is allowed only for `cache_ttl` (no cache) and `retry_after_max` (never wait); hook timeouts are whole seconds from 1 to 600; `--timeout` and the `timeout` key run from 1 s to 24 h. The caps are: `timeout`, `--timeout`, `sites.<name>.timeouts.connect` and `.read` at most 24 h, and `sites.<name>.cache_ttl` and `limits.retry_after_max` at most 365 d; a value above its cap is refused naming the key.

Loader checks that JSON Schema cannot express, all `invalid_config` naming the key: `default_site` names a configured site; a project key claimed by two sites is allowed (selection then needs `--site`); `me` and `account_id` shapes; `queries` and `extra` names collide with no logical name; `email` xor `email_env`; the `url` rules above; and hook timeouts that are whole seconds from 1 to 600. Configuration errors name the key path and the constraint, never the input value or a source line. An `email_env` or `token_env` variable that is unset or empty is exit 12 `auth_required` naming it, only for commands that call the provider (`sites` and `validate` without `--probe` never read them). A configured account expectation (`me.jira` or `account_id`) that differs from `/myself` makes a write exit 2 (`invalid_config`, `reason: account_mismatch`) before anything is sent; for reads it is a warning, and `validate --probe` reports it.

The loader treats every config file and drop-in as hostile input. Each is opened without blocking and must be a regular file (a symlink to one is followed; a FIFO, device or directory is refused), owned by the current user or root, not world-writable, at most 1 MiB and valid UTF-8; `config.d` must be a directory that is not world-writable and holds at most 64 `*.yaml` files (dotfiles and other extensions are ignored). The YAML is parsed with a safe loader that also refuses anchors, aliases, explicit tags, merge keys, duplicate keys, non-string keys and nesting deeper than 32 levels. A missing default `config.yaml` is an empty configuration (a command that needs a site then exits 2 with `reason: no_sites`); a missing `--config` file is exit 2 `config_invalid`. `sites.<name>.url` is normalized (lower-case scheme and host, default port and trailing slash dropped) and refuses percent escapes, backslashes, non-ASCII, spaces and empty, `.` or `..` path segments. A `TICKETCTL_TIMEOUT` or `TICKETCTL_DEFAULT_SITE` that is empty is treated as unset.

Per-repo overrides do not exist: ticketctl has no repository notion, and its settings are scoped by site (the position `repos:` holds elsewhere).

### Credentials

The token comes only from the environment variable named by `token_env`. A missing or empty variable exits 12 `auth_required` naming the variable. A 401 exits 12 `bad_credentials`; a 403 on any call exits 12 `forbidden`. There is no token command and no stored login. Hooks and child processes get the environment minus every configured `token_env` and `email_env` variable. The token is never written to state, logs, audit, output or hook payloads, and error text never echoes it (the output scrub of [Sanitizing](#sanitizing) is the backstop): proxy URLs are printed as `host:port`, and the top-level handler prints the exception class and a fixed message for exit 1, with a traceback only when `TICKETCTL_DEBUG` is set. Callers that run ticketctl inside a Claude session must list the token variable in claude-session's `secret_env`.

## Environment variables

Only the top-level scalars `timeout`, `default_site` and `read_only` accept `TICKETCTL_<KEY>` (`TICKETCTL_TIMEOUT`, `TICKETCTL_DEFAULT_SITE`, `TICKETCTL_READ_ONLY`), a deliberate narrowing of the design guide's nested form; nested environment keys are ignored with a `validate` warning. `TICKETCTL_HOOK`, `TICKETCTL_ID` and `TICKETCTL_OBJECT_TYPE` are hook variables, not config keys, `TICKETCTL_DEBUG` is a debug switch (a traceback for exit 1) and `TICKETCTL_LIVE` is the live-test switch. The token variable's name is whatever `token_env` says; `HTTPS_PROXY` and `NO_PROXY` are honored ([Invoking the provider](#invoking-the-provider)).

## Labels

None: ticketctl creates no long-lived objects and stores none. (The `tc-` label it adds to a created ticket is provider data, described under Dedupe.)

## TUI

None in 0.x.

## Files

Under `~/.local/state/ticketctl/` (respecting `XDG_STATE_HOME`; the same path on macOS). The directory is `0700` and files are `0600`, opened with `O_APPEND|O_NOFOLLOW|O_CREAT`; a directory or file not owned by the current uid is exit 1 `internal`.

- `cache/<site>/fields.json`, `cache/<site>/me.json`, `cache/<site>/priorities.json`, `cache/<site>/resolutions.json`: replaced atomically, refetched when missing, corrupt or older than `cache_ttl`; never holds credentials. Every file stores `{schema_version, site, url, email_sha256, fetched_at, ...}` and is discarded on any mismatch of url or email hash; `me.json` also stores `time_zone`. `priorities.json` holds the provider's priority names in order and `resolutions.json` the resolution names in order (at most 1000 each; an entry without a name makes the provider's answer exit 12 `provider_changed`); `fields.json` holds the sanitized field entries (`id`, `name`, `custom`, `schema`). A list too large to cache (over the 8 MiB file limit) is refetched on every call with one warning each time; this is accepted.
- `locks/`: a `0700` directory of 256 bucket lock files for dedupe, never removed; nothing accumulates ([Dedupe](#dedupe)).
- `audit.jsonl`: public, append-only (schema `schemas/audit.json`), kept forever.
- `log.jsonl`: public request log (schema `schemas/log.json`), rotated at 10 MiB keeping `log.jsonl.1` to `.3` under the same flock.

Appends take an `flock`, waiting at most 10 seconds (a stuck holder makes the append fail, never hang). The directory is opened without following a symlink (a symlinked ancestor is fine), a state directory or file that the current user owns but with wider permissions is set to `0700` or `0600`, and a symlink, a non-regular file (a FIFO, for example) or a foreign owner is refused. A cache file whose content is unreadable, over-long (8 MiB), of an unknown version or mismatched (another site, url or email hash, older than `cache_ttl`, or fetched more than 5 minutes in the future) is deleted and refetched, never an error; a cache or state file the user owns whose mode denies reading is set to `0600` first; a `cache_ttl` of `0` reads and writes no cache. An audit or log record over 64 KiB is refused; the limit is the only bound on the `bodies`, `files_sha256` and `provider_ids` lists, which have no `maxItems` in `schemas/audit.json`. There is no database, no `cron` command and no `reconcile` or `prune`: nothing needs maintenance.

## Audit and log

**Audit.** One record pair per provider write call (GETs are not records): `result: attempted` before the call and the outcome after. `step` numbers the write calls of the command from 1, `step_kind` is the plan step kind, and `attempt_id` is shared by the command and is in `details.attempt_id` of every failure envelope after the `attempted` record. `result` is `attempted`, `ok`, `failed` (a definite refusal or error, `changed` false), `partial` (a definite failure after an earlier step of the same command landed, `changed` false) or `unknown` (a request that may have been sent with no answer: timeout, dropped connection, 5xx on a write; `changed` null whether or not an earlier step landed); `changed` is null for `attempted` and `unknown` and a boolean otherwise; `reason` is the error code of a failed, partial or unknown outcome. The command-level exit 12 `partial` with `outcome_unknown: true` is derived from the steps. The outcome of `create` fills `target.key` (null on the `attempted` record and when the create failed). A record with no outcome means ticketctl died or could not write it.

If the outcome append fails after a send, ticketctl warns on stderr, prints the result, exits with the real outcome, and the result `warnings` has `audit_incomplete`. If the `attempted` append of a step fails, that step is not sent: with nothing landed the command exits 1 `internal` (`reason: audit_failed`); with an earlier step landed it exits 12 `partial` whose failed step carries `code: internal`. A refused send can leave an `attempted` record with no outcome: the line may reach the file before the failure that is reported (a failed `fsync`, say). Readers treat such a record like any crash, as an attempt of unknown outcome.

Fields: `v` (integer 1), `seq`, `ts`, `attempt_id`, `step`, `step_kind`, `actor`, `actor_source`, `stdin_tty`, `decision_id` (a list: hook-returned and flag ids both), `target` (`{site, key}`), `action`, `inputs`, `result`, `provider_ids`, `changed`, `reason`. `inputs` holds `plan_sha256`, `bodies` (sha256 and byte size), `dedupe_key`, `override_escalation`, `config` (`{path (null for the default location), files_sha256 (the loaded files), sha256 (the merged document)}`), `site_host` (the host and port requested), `hooks_sha256` (the effective hook list, configured plus `--hook`), `cli_hooks` (the `--hook` names) and `token_env` (the variable name, never a value), as cheap evidence of a bypass. No body text, no titles, no secrets. `seq` is assigned under the flock as 1 plus the last record's `seq` read from the file tail. `fsync` follows each `attempted` append.

**Log.** One line per provider call: `v`, `ts`, `site`, `host` (the host and port requested), `config_sha256` (the merged config), `method`, the full path template (`/rest/api/3/issue/{key}`, `/rest/agile/1.0/sprint/{id}/issue`, `{property}` for a property key; no values), `status`, `duration_ms`, `retries`, `rate_limit_remaining`. No headers, no bodies. A failed log write warns and never fails the command. `audit.jsonl` and `log.jsonl` are written with `ensure_ascii=True`; under the flock, if the last byte of the file is not `\n` a newline is written first, and if the tail line does not parse, `seq` is the maximum found by scanning the file.

## Upgrades

The interface version is semver; before 1.0 a breaking change is a `feat` whose title names the break. The cache has a `schema_version`; an unknown version is discarded and refetched. `audit.jsonl` and `log.jsonl` carry `v` and gain fields additively only (a minor release); the schemas are closed for the producer's tests and a consumer tolerates unknown properties.

## Residual risks

- The dedupe label is bound to the config's site name: renaming the site in the config, or naming the same site differently on two machines, changes the label, so a re-run finds nothing and can create a duplicate.
- The create lag guard ([Dedupe](#dedupe)) is a bound, not a guarantee: the create-to-search lag was not measured beyond the observed second for a label added by update, and 60 s of polling is a chosen limit.
- The lag guard trusts the record's clock: a `ts` far in the future (a clock stepped back) makes every same-key `create` wait up to 60 s until the clock catches up, and a `--timeout` shorter than that wait exits 12 `timeout`; waiting is safe, a duplicate ticket is not. The guard reads only the last 1 MiB of `audit.jsonl`: a same-key create record pushed out of that window (more than 1 MiB written within 120 s) skips the guard wait, a possible duplicate after an unknown outcome.
- The balance scanner of [Search compilation](#search-compilation) is a copy of Jira's lexer rules and only defense in depth; Jira's own lexing of quotes and backslashes outside strings is not verified, which is why a raw query is never combined. A named query that holds a backslash outside a string, or another construct the two lexers might read differently, is the user's own and is trusted.
- A provider validator can still reject a write the plan did not predict (`rejected`, exit 12), for example a required assignee.
- Two concurrent creates with the same dedupe key on different hosts can both succeed; same-host runs are serialized by the bucket lock and the lag guard, and a gateway 5xx on a comment may still be committing when the re-run looks.
- `plan_sha256` guards against a changed ticket, not against a hostile same-user process: the `actor` claim is not authenticated, and the controls are the caller's to choose (see [Trust boundary](#trust-boundary)): a dry-run then `--yes` with its own hash, `--config` with no hooks, `--hook`, a pty answering the prompt, and `HTTPS_PROXY` or CA variables are same-user bypasses. The audit is evidence for a cooperative caller, not a tamper-evident record.
- Jira has no optimistic locking: a write that changes a field another writer changed in the last milliseconds is last write wins per field, and the hash narrows but does not close that window. A human takeover between a plan and its apply is seen only for the facts the plan reads.
- An assign plus a transition is not atomic. An assign step that appears between plan and apply (the assignee was cleared) runs as the plan said; it was in the confirmed intent. Two keyless `--yes` runs of a `transition` or `update` that overlap can both send; benign for idempotent end states.
- The sanitizer is category based: emoji sequences (a heart with U+FE0F, joiner sequences) and text that needs U+200C (Persian) are shown and written with visible markers. Homograph hosts in links are not detected.
- A page of rich-text search or comment results with one ticket nested deeper than 400 levels is `provider_changed` for the whole page; default `search` fields and single-key reads are unaffected.
- Closed-sprint membership under the backlog call, and moving a ticket out of a closed sprint, are unverified.
- Plan `from` and `to` and every error echo carry provider text: fence it like ticket text (echoes are sanitized and capped).
- An automatic comment on a customer-facing (service management) project might be customer-visible; this is unverified.
- A driven caller can create new files with `export --to`.
- A ticket of the user's own with the same type and title can carry a planted `tc-` label (anyone who can edit it can add one, the label being derived from non-secret inputs), and the user's next `create` with that key is then `reused`, suppressing one create; the reporter, type and trimmed title match is the bound, and a fix would need a secret and break cross-host dedupe.
- `plan_sha256` has no expiry and no host binding: for `comment` and `create` the facts are empty, so a pending plan confirmed days later still applies when the intent matches, and a config edit that repoints a site name keeps old hashes valid. The caller's pending store owns the time limit.
- Comment dedupe fails closed and third parties can deny it: anyone who can comment can post 1000 newer comments (`lookup_incomplete`) or comments with large properties that push the page past the response cap (`provider_changed`), and keyed comments on that ticket then fail until a human posts without a key.
- The `ticketctl.meta` comment property, and so `actor_kind`, `authored_by_ticketctl`, `body_sha256` and `dedupe_key_sha256` of the comment object, can be set by the comment's author and by anyone with Edit All Comments: it is advisory, and `actor_kind: human` is not proof of a human.
- Strong right-to-left letters are not replaced by the sanitizer, so a bidi-aware terminal can reorder neighboring text and parentheses in the confirmation dialog; link targets stay printable ASCII, so this is cosmetic.
- Per-user transition filtering, 429 behavior, scoped API tokens, moved or archived tickets and a hidden ticket's status code were not verified live; the retry rules are conservative because of that.
- Ticket text is untrusted; ticketctl sanitizes control characters but does not fence.

## Platform notes

Pure Python: the standard library for HTTP and process-free work, with `pyyaml` and `pydantic` as the only runtime dependencies. Linux, WSL and macOS behave the same. Python 3.12 and 3.13. Timestamps are normalized to UTC; local time is never printed. There is no sandbox or process work in ticketctl.
